MVP-A: проверка осуществимости на эмуляторах

Android-агент собирает телеметрию с планшета ресторана и по MQTT 5 через TLS отправляет её на брокер Mosquitto. Обратно агент принимает настройки и команды. MVP-A проверяет эту цепочку на эмуляторах Android 8 и Android 16, до того как на ней будут строиться курсовая, практика и диплом.

Что такое MVP

RestoFleet — IoT-платформа для мониторинга и удалённого управления Android-устройствами ресторанной сети: планшетами кухни, зала и сборки. Работа рассчитана на три этапа: курсовая → практика → диплом. До старта курсовой нужно убедиться, что самые рискованные части вообще можно сделать на Android. Этим и занимается MVP.

MVP-A — эмуляторы закрыт

Нужен до курсовой. Проверено на эмуляторах API 26 (Android 8.0, минимальная версия проекта) и API 36 (Android 16, targetSdk), а также на эмуляторе API 36 в режиме Device Owner. Стенд — локальный docker compose.

MVP-B — реальные устройства впереди

Курсовую не блокирует, но должен закончиться до Device Owner в дипломе. В него входят планшет на Android 8.0 (сброс и Device Owner), телефон на Android 12, промежуточные API 29/31/33/35, API 37, ночной прогон и замер ресурсов на release-сборке.

Правило проекта: требование, получившее в матрице MVP ❌, не реализуется. ⚠️ означает, что требование остаётся, а ограничение записывается в ТЗ и в доменную модель Capabilities. В MVP-A нет ни одного ❌.

Как это работает

  1. Агент получает учётку. В MVP-A её передаёт debug-приёмник DevConfigReceiver через adb. Учётка шифруется AES-GCM ключом из Android Keystore и переживает перезагрузку.
  2. Агент подключается к брокеру по TLS. Доверяет он только CA стенда (пиннинг, проверка SAN). В CONNECT заранее кладётся «завещание» (LWT) offline.
  3. Агент публикует retained status: online и подписывается на свои shadow/desired и cmd/req.
  4. Каждые 30 секунд (интервал задаёт сервер через desired) агент собирает телеметрию и выполняет проверки доступности, результаты уходят в MQTT.
  5. При обрыве связи события копятся в outbox, а брокер сам публикует LWT offline. После восстановления агент досылает всё по порядку.
  6. Оператор отправляет команду. Агент сразу отвечает received, выполняет её и отвечает итогом (succeeded/failed/unsupported).

Жизненный цикл агента

  • Служба переднего плана типа specialUse с постоянным уведомлением. Тип выбран потому, что на него не распространяется запрет Android 15 на запуск из BOOT_COMPLETED.
  • Автозапуск после перезагрузки через BootReceiver. На API 26 агент выходит в сеть примерно через 1 с после загрузки системы.
  • Сторож WorkManager раз в 15 минут проверяет, жива ли служба.
  • PARTIAL_WAKE_LOCK держится, пока работает цикл, иначе во сне тики останавливаются. Сам цикл крутится на IO-диспетчере, а не на главном потоке.
  • Журнал жизненного цикла и heartbeat пишутся в файлы с починкой оборванного хвоста.

Подключение к брокеру

MqttBrokerSession реализует доменные порты BrokerSession и MessagePublisher. Библиотека HiveMQ спрятана за тонкой границей MqttLink, поэтому сессию можно тестировать без сети. Подключение идёт в таком порядке:

  1. Прочитать учётку. При временном сбое Keystore агент повторяет попытку и учётку не стирает.
  2. Загрузить CA стенда. Если CA нет, агент не подключается (ca_missing).
  3. Отправить CONNECT с завещанием status offline/lwt и свежим connId на каждую попытку.
  4. Опубликовать retained online с тем же connId. По нему отличают LWT старой сессии от новой.
  5. Подписаться на shadow/desired и cmd/req с QoS 1, затем дослать outbox.

Повторы: обычные ошибки — через 1…120 с с нарастанием. Неверная учётка (auth_failed) — через 15 → 30 → 60 мин, чтобы не бить брокер. Вытеснение сессией с тем же clientId (session_taken_over) — через 5 мин с разбросом. Смена учётки перезапускает сессию сразу.

Outbox: доставка без потерь

  • События, shadow/reported и cmd/res сначала записываются в Room и удаляются только после PUBACK брокера.
  • Телеметрия и пробы при наличии связи идут сразу (QoS 0). Без связи они тоже попадают в буфер.
  • Вместимость 10 000 записей. При переполнении вытесняется наименее важное: сначала телеметрия.
  • Досылка идёт пачками по 50, порядок seq сохраняется. Итог команды не ждёт, пока уйдёт вся накопленная телеметрия.
  • Если брокер окончательно отверг запись (PUBACK 0x87, 0x90, 0x97, 0x99), она удаляется, чтобы не блокировать очередь.

Команды

  • Команда приходит в cmd/req со свойствами MQTT 5: Response Topic, Correlation Data, Message Expiry. В теле команды есть cmdId и expiresAt.
  • Агент сразу отвечает received, выполняет команду и отвечает итогом. Correlation Data возвращается в ответе.
  • Команду с истёкшим expiresAt агент не выполняет. Повторы отсекаются по журналу обработанных команд (200 последних): каждая команда выполняется не больше одного раза.
  • Подтверждение (ack) брокеру уходит после обработки, а не при получении. Поэтому команда не теряется, если агент упал посреди работы.
  • Модель Capabilities (режим normal/DO, API, разрешения, киоск) решает, можно ли выполнить команду. Если нельзя, агент отвечает unsupported с причиной, а под киоском — failed/kiosk_active вместо ложного успеха.

Тень: desired и reported

Сервер публикует retained shadow/desired с версией: интервал телеметрии, пороги, отслеживаемые приложения, цели проб. Агент получает его при каждом подключении, применяет и отвечает shadow/reported с appliedVersion. Неверный интервал (вне 10…3600 с) не применяется: остаётся прежний, а причина пишется в errors.

Device Owner

Если агент назначен владельцем устройства (dpm set-device-owner на эмуляторе без аккаунтов, на реальном устройстве — после сброса), ему доступны:

  • перезагрузка;
  • тихая установка APK по URL с проверкой SHA-256 через PackageInstaller;
  • киоск (lock task);
  • запуск приложений из фона;
  • самовыдача разрешений: геолокации, уведомлений, READ_PHONE_STATE. Usage Access так выдать нельзя;
  • чтение серийного номера (в отчёт он попадает только в маске) и температур через HardwarePropertiesManager.

Экран, где эти действия запускаются вручную, существует только в debug-сборке. В release DO-команды приходят лишь по MQTT и ограничены отслеживаемыми пакетами.

Безопасность

Транспорт и брокер

  • Только TLS на 8883, порта 1883 нет, анонимы запрещены.
  • Свой CA стенда. Агент доверяет только ему и только в debug-сборке, в release CA стенда не доверяется.
  • Dynamic Security: роль device «всё запрещено, кроме своих топиков», clientId привязан к учётке.
  • Пароль устройства — 32 случайных байта, хранится в deploy/out/ вне git.
  • disableClient разрывает сессию устройства за 16 мс.

Агент и процесс

  • Учётка зашифрована ключом Android Keystore. В открытом виде её нет ни в SharedPreferences, ни в логах.
  • Ключ и учётка стираются только при необратимой порче, при временных сбоях они сохраняются.
  • Опасные debug-функции (экран DO, ручные команды, приём учётки) в release отсутствуют. Это проверяют тесты *ReleaseTest и задача verifyReleaseNoDebugSurface.
  • Пароли не попадают в аргументы команд на хосте: скрипты передают их через stdin. Исключение: внутри эмулятора пароль виден в аргументах am broadcast debug-приёмника. Это принятое ограничение отладочного инструмента.
  • Перед каждым коммитом история проверяется на утечку секретов.

Как протестировать

Четыре уровня, от быстрого к подробному. Все команды выполняются из корня репозитория. Пароли читаются из файлов и на экран не выводятся. Не вставляйте их в чаты и тикеты.

Уровень 1. Сборка и тесты (≈ 5 мин, без устройства)

./gradlew build detekt koverVerifyCi :konsist-tests:test --continue

Ожидается BUILD SUCCESSFUL: 1289 тестов, lint и detekt без ошибок, покрытие выше порогов (domain и data ≥ 90 %, проект ≥ 80 %). Отчёт покрытия — build/reports/kover/. Для сборки нужен local.properties с sdk.dir.

Уровень 2. Стенд

Первый запуск на новой машине (из deploy/). Шаги с пометкой «один раз» выполняются один раз:

cd deploy
cp .env.example .env && sed -i '' "s|change-me|$(openssl rand -base64 32 | tr -d '/+=')|" .env   # один раз
./certs/make-ca.sh                                   # один раз: CA и серверный сертификат
docker compose --profile init run --rm dynsec-init   # один раз: администратор DynSec
docker compose up -d --wait                          # брокер и APK-хост
mosquitto/dynsec-dev.sh                              # роли и dev-учётки, пароли → out/dev-credentials.txt
../tools/dev/build-dummy-apk.sh 13                   # один раз: APK для проверки установки

Проверка стенда:

cd deploy
./test-stand.sh                  # TLS, отказ анонимам и чужому паролю, нет 1883, нет ca.key в контейнере
mosquitto/test-dynsec-dev.sh     # ACL устройств: ожидается 16 PASS из 16

CA стенда встраивается в debug-сборку агента при сборке. Поэтому агента нужно собирать после make-ca.sh, иначе он не подключится (ca_missing).

Уровень 3. Автоматический прогон на эмуляторе

./gradlew :agent:app:assembleDebug
tools/emulators/run-matrix.sh rf-api36 36

Скрипт делает следующее:

  • поднимает эмулятор без окна и ставит агента;
  • передаёт учётку через stdin;
  • ждёт online и телеметрию;
  • проверяет автозапуск после adb reboot;
  • делает экспорт из Lab.

Уровень 4. Вручную, с интерфейсом

  1. Эмулятор и агент. Запустите AVD rf-api36 из Device Manager в Android Studio и запустите конфигурацию agent.app. tools.dummy-waiter запускать не нужно, это цель для команд.
  2. Терминал A — подписка оператора (пароль оператора попадает только в файл с правами 600 внутри контейнера): 
    cd deploy; PW=$(awk '$1=="operator"{print $2}' out/dev-credentials.txt)
{ printf 'umask 077\nmkdir -p /tmp/rfopt\n'; for t in mosquitto_sub mosquitto_pub; do
  printf "cat > /tmp/rfopt/%s <<'EOF'\n-h localhost\n-p 8883\n-V mqttv5\n--cafile /mosquitto/certs/ca.crt\n-u operator\n-P %s\nEOF\n" "$t" "$PW"; done; } | docker compose exec -T mosquitto sh -s; unset PW
O() { docker compose exec -T -e XDG_CONFIG_HOME=/tmp/rfopt mosquitto "$@"; }
O mosquitto_sub -t 'rf/v1/dev/dev-emu-36/#' -v -F '%U %t %p'
  3. Терминал B — учётка для агента (из корня репозитория): 
    PW="$(awk '$1=="dev-emu-36"{print $2}' deploy/out/dev-credentials.txt)"
printf 'am broadcast -a ru.restofleet.agent.DEV_CONFIG -n ru.restofleet.agent/.DevConfigReceiver --es host 10.0.2.2 --ei port 8883 --es deviceId dev-emu-36 --es password %s\n' "$PW" | adb shell sh
unset PW
    Ожидается Broadcast completed: result=-1, data="ok". Если пришло result=0, в data будет код ошибки.

По желанию: Device Owner на rf-api36-do

На обычном rf-api36 агент не Device Owner, и проверки экрана «Владелец» там не пройдут. Запустите AVD rf-api36-do, установите агента и передайте ему учётку dev-do-36 той же командой (поменяйте имя в двух местах).

  • «Запустить все проверки DO».
  • Тихая установка (D3). Адрес APK: https://10.0.2.2:8443/waiter-4.13.apk, затем «Подтянуть хэш» и запуск D3. Приложение ставится без диалогов. Для проверки обновления есть waiter-4.14.apk.
  • Перезагрузка (D2). Агент просит подтверждение, перезагружает устройство и возвращается сам.

MVP-B

Реальный планшет на Android 8.0 (сброс, Device Owner, регистрация по QR, ночь с выключенным экраном), телефон на Android 12, API 29/31/33/35 и 37, сторож L3, замер памяти и трафика на release-сборке.

Курсовая

Минимальное ядро: протокол + агент + брокер + бэкенд Ktor + симулятор устройств + эксперимент MQTT против REST-polling. Консоли пока нет.

Практика и диплом

Практика: тревоги, инциденты, Android-консоль. Диплом: Device Owner в продукте, Desktop-консоль, масштаб 10 000 устройств, развёртывание на VPS.
