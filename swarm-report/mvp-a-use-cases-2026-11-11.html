Подготовка к проверкам

Стенд поднят по deploy/README.md, агент собран (./gradlew :agent:app:assembleDebug) и запущен на эмуляторе. Пароли читаются из файлов и на экран не выводятся. Команды проверены в zsh и bash.

Терминал A: подписка оператора на все сообщения устройства (из каталога deploy/):

cd deploy
PW=$(awk '$1=="operator"{print $2}' out/dev-credentials.txt)
{ printf 'umask 077\nmkdir -p /tmp/rfopt\n'; for t in mosquitto_sub mosquitto_pub; do
  printf "cat > /tmp/rfopt/%s <<'EOF'\n-h localhost\n-p 8883\n-V mqttv5\n--cafile /mosquitto/certs/ca.crt\n-u operator\n-P %s\nEOF\n" "$t" "$PW"; done; } | docker compose exec -T mosquitto sh -s; unset PW
O() { docker compose exec -T -e XDG_CONFIG_HOME=/tmp/rfopt mosquitto "$@"; }
DEV=dev-emu-36          # для Device Owner: DEV=dev-do-36
O mosquitto_sub -t "rf/v1/dev/$DEV/#" -F '%I %t %p'

Терминал B: учётка агенту и отправка команд (из корня репозитория, затем deploy/):

DEV=dev-emu-36          # для Device Owner: DEV=dev-do-36
PW="$(awk -v u="$DEV" '$1==u{print $2}' deploy/out/dev-credentials.txt)"
printf 'am broadcast -a ru.restofleet.agent.DEV_CONFIG -n ru.restofleet.agent/.DevConfigReceiver --es host 10.0.2.2 --ei port 8883 --es deviceId %s --es password %s\n' "$DEV" "$PW" | adb shell sh
unset PW

cd deploy
O() { docker compose exec -T -e XDG_CONFIG_HOME=/tmp/rfopt mosquitto "$@"; }
rfcmd() { # rfcmd <type> '<params JSON>' [срок в секундах: по умолчанию 300, отрицательный — уже истёк]
  python3 -I -c 'import json,sys,time;print(json.dumps({"cmdId":"c-man-%d"%(time.time()*1000),"type":sys.argv[1],"params":json.loads(sys.argv[2]),"expiresAt":int(time.time()*1000)+int(sys.argv[3])*1000},ensure_ascii=False),end="")' "$1" "$2" "${3:-300}" \
  | O mosquitto_pub -q 1 -t "rf/v1/dev/$DEV/cmd/req" -D publish response-topic "rf/v1/dev/$DEV/cmd/res" \
      -D publish correlation-data c-man -D publish message-expiry-interval 300 -s
}

Если нет нескольких эмуляторов, adb работает без -s. После проверок удалите опции оператора: docker compose exec -T mosquitto rm -rf /tmp/rfopt. Большую часть сценариев можно прогнать без ручных шагов: tools/emulators/run-matrix.sh rf-api36 36 [--window] и tools/emulators/run-matrix.sh rf-api36-do 36 --do [--window]. Весь MQTT-обмен прогона попадает в logs/run-matrix/.

Подключение и связь

UC-01

Подключить устройство к платформе

✅ L5✅ M1

Кто и зачем: техник при установке планшета. Устройству нужна собственная учётка брокера, чтобы отправлять данные и получать команды.

Как проходит

  1. На брокере создаётся клиент Dynamic Security с ролью device. Сейчас это делает deploy/mosquitto/dynsec-dev.sh, в продукте будет делать бэкенд при провижининге.
  2. Агент получает учётку: адрес, порт, deviceId и пароль. В MVP-A она передаётся debug-командой через adb.
  3. Агент шифрует и сохраняет учётку, после чего перезапускает MQTT-сессию.
  4. Агент подключается по TLS и публикует status: online.

Под капотом

  • DevConfigReceiver защищён разрешением DUMP, которое есть только у оболочки adb.
  • ConfigureBrokerCredentials проверяет поля учётки.
  • KeystoreCredentialStore шифрует учётку AES-GCM ключом из Android Keystore.
  • NotifyingCredentialStore перезапускает сессию после смены учётки.
  • CA стенда встраивается в debug-сборку при сборке.
Результат MVP-A: учётка переживает adb reboot на API 26 и 36. В прогонах 11.11 агент вышел в сеть через 0–2 с после передачи учётки.
Как попробовать

Терминал B из раздела «Подготовка». Ожидается Broadcast completed: result=-1, data="ok", а в терминале A — status с online.

Ограничения: передача через adb работает только в debug-сборке, в release этого приёмника нет. Внутри эмулятора пароль виден в аргументах am broadcast. Провижининг по QR (D7) и токену — MVP-B и курсовая.

UC-02

Видеть, на связи ли устройство

✅ M3

Кто и зачем: поддержка. Нужно понимать, «живо» ли устройство, не звоня в ресторан.

Как проходит

  1. При подключении агент публикует retained status со state: online и новым connId.
  2. При обрыве связи брокер сам публикует «завещание» (LWT) offline с reason: lwt.
  3. При переподключении приходит online с другим connId. Запоздавший LWT старой сессии узнаётся по старому connId.

Под капотом

  • LWT задаётся заранее в CONNECT, keepalive 30 с.
  • connId генерируется заново на каждую попытку подключения.
  • В status есть также bootId, модель, версия ОС и mode (normal или device_owner).
Результат MVP-A: после выключения сети offline пришёл через 23 и 43 с (ожидание ≈ 45 с, допуск ≤ 75 с).
Как попробовать 
adb shell 'svc wifi disable; svc data disable'   # через 30–45 с в терминале A: offline, тот же connId
adb shell 'svc wifi enable; svc data enable'     # online с новым connId

Ограничения: offline приходит не сразу, а за время до полутора keepalive.

UC-03

Не терять данные без связи

✅ M7✅ P4

Кто и зачем: поддержка. После обрыва нужно увидеть всё, что происходило, пока устройство было офлайн.

Как проходит

  1. Без связи каждое исходящее сообщение записывается в локальную очередь (outbox).
  2. После подключения очередь досылается пачками по 50 в исходном порядке.
  3. Запись удаляется только после подтверждения брокера (PUBACK).

Под капотом

  • PublishOrBuffer и FlushOutbox, хранение — Room.
  • Вместимость 10 000 записей. При переполнении вытесняется наименее важное, первой уходит телеметрия.
  • Окончательный отказ брокера (PUBACK 0x87, 0x90, 0x97, 0x99) удаляет запись, чтобы она не блокировала очередь.
  • Итоги команд досылаются отдельно и не ждут телеметрию.
Результат MVP-A:
  • 500 событий после 5,6 мин офлайна дошли без пропусков и дублей.
  • При остановке брокера на 125 с все 8 проб досланы по порядку.
  • В DO-прогоне 11.11 события ручной сессии, пока у агента не было учётки, пришли все разом через 10 минут, как только учётка появилась.
Как попробовать 
adb shell 'svc wifi disable; svc data disable'
# в Capability Lab: «Отладка» → «Сгенерировать N событий»
adb shell 'svc wifi enable; svc data enable'     # в терминале A: события debug_seq с непрерывным seq
# простой брокера (подписка в терминале A при этом оборвётся, её нужно перезапустить):
cd deploy && docker compose stop mosquitto && sleep 125 && docker compose start mosquitto
Ограничения:
  • Офлайн проверялся минутами, а не сутками.
  • У событий нет собственного идентификатора, поэтому при обрыве досылки возможен одиночный дубль.
  • После перезапуска агента seq телеметрии начинается с 1. См. также наблюдения о задержке до 60 с.
UC-04

Работать без участия персонала

✅ L2⚠️ L4⏳ L3— L1

Кто и зачем: ресторан. Агент не должен требовать внимания сотрудников и должен сам подниматься после сбоев и перезагрузок.

Как проходит

  1. Агент работает как служба переднего плана с постоянным уведомлением.
  2. После перезагрузки он запускается сам, приложение открывать не нужно.
  3. Сторож WorkManager раз в 15 минут проверяет, жива ли служба.
  4. Мастер разрешений просит выдать уведомления, Usage Access и исключение из оптимизации батареи.

Под капотом

  • Тип службы specialUse: на него не распространяется запрет Android 15 на запуск из BOOT_COMPLETED.
  • BootReceiver и WatchdogWorker.
  • PARTIAL_WAKE_LOCK держится, пока работает цикл.
  • Журнал жизненного цикла пишется в файл. В MQTT уходит событие agent_lifecycle (start или boot).
Результат MVP-A:
  • L2 ✅: агент снова в сети через 1–4 с после загрузки на API 26 и 36. На DO-планшете — через 23 с.
  • L4 ⚠️: Usage Access и исключение из оптимизации батареи выдаются только вручную.
  • L3 (сторож) не проверялся.
  • L1 (12 часов со спящим экраном) перенесён на реальный планшет.
Как попробовать 
adb reboot          # приложение не открывать; в терминале A — новый online не позже чем через 3 мин
tools/emulators/run-matrix.sh rf-api36 36 --window    # то же автоматически: строка L2_reboot

Ограничения: энергосбережение прошивок реальных производителей не проверено (MVP-B).

Мониторинг

UC-05

Следить за состоянием устройства (телеметрия)

✅ R1 R2 R4 R6 R7 R9 R14⚠️ R3 R5 R8 R11

Кто и зачем: поддержка. Нужно видеть заряд, перегрев, качество сети, свободную память и то, какое приложение открыто на кухне.

Как проходит

  1. Каждые intervalSec (по умолчанию 30 с, задаётся в desired) агент собирает считывания.
  2. Результат публикуется в telemetry: при связи сразу, без связи — в очередь.

Что внутри

  • battery: уровень, зарядка, источник, температура.
  • thermal: статус и тепловой запас.
  • net: тип, RSSI, validated.
  • storage.freeMb, memory.availMb, uptimeSec.
  • foregroundApp и версии отслеживаемых приложений.
  • seq и ts.

Под капотом

  • CollectTelemetry изолирует сбой каждого считывания: недоступное значение не роняет цикл и не ломает сообщение.
  • Сборщики находятся в agent:data/collectors.
Результат MVP-A: большая часть считываний работает на API 26 и 36. Ограничения (⚠️):
  • теплового статуса нет на API 26 (он есть с API 29);
  • SSID доступен только с геолокацией;
  • активное приложение — только с Usage Access;
  • датчика significant motion на эмуляторе нет.
Как попробовать 
O mosquitto_sub -t "rf/v1/dev/$DEV/telemetry" -F '%I %p'

Ограничения: пороги из desired (batteryLowPct, tempHighC, fgAbsentMin) агент не проверяет, это задача бэкенда (практика). Реальные значения датчиков — MVP-B.

UC-06

Проверять доступность сервисов ресторана

✅ P1–P4 на 26⚠️ P1 P2 на 36

Кто и зачем: поддержка. Нужно отличать «упал сервис компании» от «у ресторана пропал интернет» и видеть, на каком этапе рвётся соединение.

Как проходит

  1. Цели приходят в desired.probes: id, url, intervalSec, timeoutMs.
  2. Каждая цель опрашивается по своему интервалу, первый раз — сразу.
  3. Результат публикуется в probe: ok, HTTP-статус, длительность фаз dnsMs/connectMs/tlsMs/ttfbMs и класс ошибки.
  4. Отдельно проверяется шлюз в локальной сети (P3).
  5. При недоступном брокере пробы не останавливаются, результаты копятся в очереди (P4).

Под капотом

  • OkHttp и EventListener для замера фаз.
  • Классы ошибок: dns_fail, timeout, conn_refused, tls_error, http_4xx/5xx, no_network.
  • ProbeLoop перезапускается при смене набора целей.
Результат MVP-A:
  • Классы ошибок и фазы соединения работают.
  • На API 36 тестовая цель Capability Lab по умолчанию упала по таймауту, а рабочие пробы цикла дают 200/204/200.
  • Пример из прогона 11.11: gstatic ответил 204 за 464 мс, из них TLS — 183 мс.
Как попробовать 
O mosquitto_sub -t "rf/v1/dev/$DEV/probe" -F '%I %p'
# набор целей меняется через desired — см. UC-08

Ограничения: событие probe_state (цель «упала» или «поднялась» после failThreshold неудач) описано в протоколе, но в MVP агент его не публикует. Это решает бэкенд по сырым результатам (решение 3.6b). Разрешение на локальную сеть в Android 17 не проверено.

UC-07

Узнавать о событиях устройства

✅ R14✅ R12 (DO-прогон 11.11)

Кто и зачем: поддержка. Нужно знать, что сменилась сеть, обновилось приложение официанта или перезапустился агент.

Какие события

  • net_changed: тип сети, validated, RSSI.
  • package_changed: added, replaced или removed для отслеживаемых приложений, с versionCode.
  • agent_lifecycle: start или boot.
  • capability_check: отправляется из Capability Lab.
  • debug_seq: только для отладки.

Под капотом

  • EventPump слушает сеть, пакеты и жизненный цикл.
  • События идут через outbox и потому не теряются.
  • Отслеживаемые приложения — статический список и desired.watchedApps.
Результат MVP-A: смена сети работает. В DO-прогоне 11.11 пришли package_changed removed → added (4.13) → replaced (4.14). В матрице на 10.11 у R12 стоит ⚠️ («событий в прогоне не было»), теперь событие наблюдалось.
Как попробовать 
O mosquitto_sub -t "rf/v1/dev/$DEV/events" -F '%I %p'
adb uninstall ru.restofleet.dummy.waiter      # package_changed removed (если приложение стояло)

Ограничения: на одно изменение пакета приходит по два события (removed × 2, replaced × 2 в пределах миллисекунд). Бэкенду нужна дедупликация. События могут задерживаться до 60 с, см. наблюдения.

Удалённая настройка

UC-08

Настраивать агент удалённо (desired → reported)

✅ M4

Кто и зачем: оператор, а в продукте — бэкенд. Нужно менять интервал телеметрии, список приложений и цели проб, не выезжая к устройству.

Как проходит

  1. Сервер публикует retained shadow/desired с номером версии.
  2. Агент получает его при каждом подключении и применяет, только если версия новее уже применённой.
  3. Агент отвечает shadow/reported с appliedVersion, appliedAt и errors.

Под капотом

  • ApplyDesiredShadow.
  • Тень хранится в файле (FileShadowStore) и переживает перезапуск.
  • Неверный intervalSec (вне 10…3600) не применяется, остаётся прежний, причина пишется в errors.
  • Неверные имена пакетов попадают в errors как watchedApps:invalid_name:<имя>.
Результат MVP-A: v12 вернулась в reported как 12, в том числе после перезапуска. v13 с тремя целями применилась за < 1 с.
Как попробовать

Взять текущий desired, поднять версию на 1 и поменять интервал на 60 с:

O mosquitto_sub -t "rf/v1/dev/$DEV/shadow/desired" -C 1 -W 5 -F '%p' \
  | python3 -I -c 'import json,sys;d=json.load(sys.stdin);d["version"]+=1;d["telemetry"]["intervalSec"]=60;print(json.dumps(d),end="")' \
  | O mosquitto_pub -r -q 1 -t "rf/v1/dev/$DEV/shadow/desired" -s
# в терминале A: shadow/reported с новым appliedVersion, телеметрия раз в 60 с

У dev-do-36 retained desired пока нет. Опубликуйте сначала фикстуру: O mosquitto_pub -r -q 1 -t "rf/v1/dev/$DEV/shadow/desired" -s < ../docs/protocol/fixtures/shadow-desired.json. В её пробах адреса-заглушки *.example, поэтому они покажут dns_fail, и это тоже наглядно.

Ограничения: пороги агент не применяет, а только возвращает эхом. Слишком большая версия «заморозит» устройство: меньшие версии оно применять не будет. Поэтому поднимайте версию на 1.

Команды в обычном режиме

UC-09

Надёжно доставлять команды

✅ M5✅ M6

Кто и зачем: оператор. Команда должна дойти ровно один раз, не выполниться устаревшей, а её результат должен вернуться отправителю.

Как проходит

  1. Команда публикуется в cmd/req со свойствами MQTT 5: Response Topic, Correlation Data, Message Expiry. В теле команды есть cmdId и expiresAt.
  2. Агент сразу отвечает received.
  3. Затем приходит итог: succeeded (с result), failed или unsupported (с reason).
  4. Если устройство офлайн, команда ждёт его на брокере, пока не истечёт срок Message Expiry.
  5. Команду с истёкшим expiresAt агент не выполняет и отвечает failed/expired.

Под капотом

  • HandleIncomingCommand, CommandMapper, ExecuteCommand.
  • Подтверждение брокеру уходит после обработки, поэтому падение посреди работы команду не теряет.
  • Повторный cmdId не выполняется: журнал помнит 200 последних команд.
  • Capabilities решает, можно ли выполнить команду. Если нельзя, приходит unsupported с причиной.
  • Команды: ping, show_message, launch_app, beep, а также reboot, install_update, lock_task — только для Device Owner.
Результат MVP-A:
  • Команда прошла путь received → succeeded за 30 мс, Correlation Data вернулась.
  • Агент был остановлен на 61 с, команда со сроком 300 с выполнилась после его старта.
  • Команда со сроком 30 с за то же время не была доставлена.
Как попробовать 
rfcmd ping '{}'                                         # received → succeeded
rfcmd show_message '{"text":"Просрочено"}' -60          # failed, reason=expired
adb shell am force-stop ru.restofleet.agent             # устройство «офлайн»
rfcmd show_message '{"text":"Пока вас не было"}'
adb shell am start -n ru.restofleet.agent/.MainActivity # команда выполнится после подключения
rfcmd reboot '{}'                                       # на обычном устройстве: unsupported, requires_device_owner

Ограничения: expiresAt сравнивается с часами устройства. Если часы уйдут вперёд больше чем на 5 минут, все команды получат expired (открытый вопрос OQ-1 в ТЗ).

UC-15

Установить или обновить приложение без участия персонала (D3)

✅

Кто и зачем: поддержка. Нужно выкатить новую версию приложения официанта на все планшеты сразу.

Как проходит

  1. Приходит команда install_update с параметрами package, url (https) и sha256 (64 hex-символа).
  2. Агент скачивает APK, сверяет SHA-256 и ставит его через PackageInstaller без диалогов.
  3. В result возвращаются package, versionCode и versionName. Параллельно приходит событие package_changed.

Отказы

  • Пакет не из списка отслеживаемых — package_not_watched. Это граница доверия.
  • Хэш не совпал — hash_mismatch.
  • Уже идёт установка — install_in_progress.
  • Неверные параметры — invalid_package, invalid_url или invalid_sha256.
Результат MVP-A (DO-прогон 11.11): установка 4.13 с нуля и обновление до 4.14 прошли со статусом succeeded и без диалогов, каждая примерно за 1,5 с.
Как попробовать 
SHA=$(awk '{print $1}' apk/waiter-4.14.apk.sha256)      # из deploy/; APK собирает tools/dev/build-dummy-apk.sh 14
rfcmd install_update "{\"package\":\"ru.restofleet.dummy.waiter\",\"url\":\"https://10.0.2.2:8443/waiter-4.14.apk\",\"sha256\":\"$SHA\"}"

Ограничения: сервер, который шлёт desired и install_update, считается доверенным. Подписанный список разрешённых приложений — кандидат в требования ТЗ.

UC-21

Изолировать устройства и отзывать доступ

✅ M2✅ S3

Кто и зачем: безопасность. Украденный или взломанный планшет не должен ни читать чужие данные, ни выдавать себя за другое устройство, а его доступ должен отзываться мгновенно.

  • Каждое устройство пишет и читает только топики rf/v1/dev/<своё имя>/…, право задаётся ACL роли device по %u.
  • clientId обязан совпадать с именем учётки.
  • Публикация в чужой топик отклоняется кодом PUBACK 0x87 (not_authorized).
  • disableClient разрывает текущую сессию и запрещает повторный вход.
Результат MVP-A: тест прав доступа проходит 16 из 16. disableClient разорвал сессию через 16 мс, повторный вход отклонён.
Как попробовать 
# в Capability Lab: «Отладка» → «Публикация в чужой топик» → «Чужой топик: not_authorized»
cd deploy && mosquitto/test-dynsec-dev.sh        # 16 PASS из 16

Ограничения: отзыв доступа в продукте будет делать бэкенд (курсовая).

UC-22

Выдержать много устройств на одном брокере

⚠️ S1✅ S2

Кто и зачем: платформа. Это нужно для эксперимента в курсовой и для симулятора тысяч устройств.

Результат MVP-A:
  • 1000 MQTT-клиентов в одном JVM-процессе 3 минуты: потерь 0, heap ≈ 114 МБ, 32,9 сообщ/с.
  • Брокер при этом занимал 37 МиБ при загрузке CPU ≈ 1 %.

Как попробовать

Ограничения: 10 000 клиентов не запускались, это экстраполяция: heap ≤ 1,1 ГБ, ≈ 80 % ядра. На macOS ограничение — примерно 16 000 эфемерных портов. Полный замер перенесён на практику.

Наблюдения из прогонов 11.11

  • Задержка событий до 60 с при живой связи. PublishOrBuffer отправляет сообщение сразу, только если outbox пуст. Если там что-то осталось, новое сообщение встаёт в очередь, а очередь досылается при подключении и затем раз в 60 с. Итоги команд идут с приоритетом и этого не ждут. В DO-прогоне события установки (package_changed) пришли через 62 с, уже после перезагрузки. Для курсовой стоит решить, допустимо ли это, или досылать очередь сразу после её опустошения.
  • Двойные package_changed. На одно удаление или обновление приходит по два события.
  • seq телеметрии сбрасывается при перезапуске агента. bootId есть в status, но в телеметрии его нет.
  • Долгий выход в сеть после перезагрузки на DO-планшете: 23 с против 2–4 с на обычном AVD.
  • Сторож L3 не проверен ни в одном прогоне.
