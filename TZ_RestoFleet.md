Протокол (разд. 7)
- Внесены правки протокола P1–P10 (арх. разд. 7); keepalive 30 с вместо 60 с, R-01 по LWT (арх. P7; матрица MVP, M3).
- P2 уточнён: `expiresAt` в `cmd/req` плюс MQTT 5 Message Expiry; агент не исполняет истёкшую команду и отвечает `failed` / `expired` (реш. 11, 135).
- Идемпотентность и порядок команд: последние 200 `cmdId` хранятся персистентно; порядок `received` → отметка → исполнение → итог; таймауты исполнения (реш. 10, 130, 131, 142).
- Формат `cmd/res`: статусы `received` / `succeeded` / `failed` / `unsupported`; `result` — объект со строковыми значениями, пустой — `{}`; у `received`, `failed`, `unsupported` поля `result` нет; коды причин (реш. 123, 135, 151).
- Допустимые значения `level` команды `show_message`: `info`, `warning`, `critical` (реш. 89).
- Поля `status`: `connId`, `bootId`, `device`; `role` опускается, если агент её не знает; штатная остановка — `offline` с `reason=stop` (реш. 150, 151).
- Валидация `desired`: `telemetry.intervalSec` 10..3600; неверное значение не применяется (остаётся прежний применённый интервал, без прежнего — 30 с), причина — в `errors` (реш. 134, 177, Ruling 279).
- Повторы подключения по причине: `auth_failed` — 15, 30, 60 мин; `session_taken_over` (0x8E) — 5 мин + jitter до 1 мин; прочие сбои — 1..120 с (реш. 152, 173, 176).
- Outbox: окончательные отказы брокера на PUBACK (0x87, 0x90, 0x97, 0x99) удаляются, временные (0x80, 0x83, 0x91) — нет; досылка пачками по 50 не быстрее 20/с, итоги команд идут вне очереди телеметрии (реш. 132, 133, 171, 172).
- Входящие сообщения QoS 1 подтверждаются брокеру после обработки (арх. P10); повторная доставка отбрасывается по `cmdId` (реш. 149).
- Записан контракт дедупликации: `cmd/res` — по `(cmdId, status)`; у событий идентификатора нет, при обрыве досылки возможен один дубль; ключ для событий — OQ-2 (M3-review; реш. 133).
- `expiresAt` сверяется с часами устройства; допуск на рассинхронизацию часов — OQ-1 (M3-review).
- Классы ошибок проверок дополнены `local_network_denied` и `other`; `connectMs` — только TCP, без TLS (реш. 38, 39, 127).

Безопасность и режимы агента
- Граница доверия: сервер — единый доверенный субъект для `desired` и `install_update`; `install_update` ставит только пакет из `watchedApps`; подписанный allowlist — кандидат (реш. 143, 161).

## 2. Назначение и цели создания системы

### 2.1 Назначение
Система предназначена для непрерывного мониторинга технического состояния устройств, установленных в ресторанах и кафе (планшеты кухонной станции, устройства официантов и сборщиков), контроля доступности серверной части компании **с точки зрения ресторанов** и удалённого управления устройствами силами службы поддержки.

### 2.2 Цели
1. Выявлять отказ устройства (потеря связи, разряд, перегрев, закрытое рабочее приложение) до того, как это приведёт к потере заказа или обращению из ресторана.
2. Быстро определять **причину** недоступности: устройство, сеть конкретного ресторана или бэкенд компании (глобально или только для части ресторанов).
3. Сократить время диагностики инцидентов службой поддержки за счёт данных о состоянии устройства и сети на момент инцидента.
4. Обеспечить централизованное управление параметрами агентов и контроль факта их применения.

### 2.3 Критерии достижения целей (проверяются на стенде)
| Критерий | Целевое значение |
|---|---|
| Время обнаружения пропажи устройства | ≤ 2 мин |
| Время обнаружения недоступности бэкенда с устройств | ≤ 2 мин (3 неудачные проверки подряд при интервале 30 с) |
| Корректная классификация инцидента (устройство / сеть ресторана / бэкенд глобально / бэкенд локально) на сценариях симулятора | ≥ 90 % |
| Глобальный отказ бэкенда порождает одну сводную тревогу, а не тревогу на каждое устройство | 1 тревога |
| Применение изменённых параметров на онлайн-устройствах | ≤ 1 мин |

## 3. Характеристика объекта автоматизации

### 3.1 Программные продукты компании (контекст)
| Продукт | Пользователи | Где работает | В контуре RestoFleet |

| Приложение официанта | Официанты | Нативное приложение на устройствах в зале | ✅ |
| Приложение сборщика | Сборщики заказов | Нативное приложение на устройствах сборки | ✅ |
| Два приложения доставки | Клиенты | Смартфоны клиентов | ❌ |
| Приложение курьера | Курьеры | Смартфоны курьеров | ❌ (план развития) |
| Приложение хостес | Хостес, колл-центр | — | ❌ |
| Бэкенд компании | Все приложения | Сервер | Только как цель проверок доступности |
| СУ — система учёта | Бэк-офис | Сервер | ❌ (настройки СУ доставляются на устройства через бэкенд; интеграция — план развития) |

### 3.2 Устройства в контуре системы
В каждом ресторане несколько устройств трёх ролей:
- **Кухня** — Android-планшеты, на которых в браузере открыта кухонная станция;
- **Зал** — Android-устройства с приложением официанта;
- **Сборка** — Android-устройства с приложением сборщика.

MDM-системы и режима киоска на устройствах нет.

### 3.3 Существующие проблемы
- Обращений в поддержку много; значительная часть связана с тем, что **бэкенд не работает или не отвечает**. Из ресторана сложно понять, в чём причина: в сети ресторана, у провайдера или на стороне сервера.
- Отказ устройства обнаруживается только после обращения ресторана.
- Нет данных о состоянии устройства на момент инцидента (заряд, сеть, версия приложения, какое приложение было открыто).
- Нет централизованного представления о парке устройств (модели, версии Android, версии приложений).

## 4. Термины и сокращения

| Термин | Определение |
|---|---|
| IoT-узел, устройство | Android-устройство с установленным агентом, публикующее телеметрию и принимающее команды |
| Агент | Отдельное Android-приложение RestoFleet Agent, работающее в фоне (foreground service) |
| Брокер | MQTT-брокер, маршрутизирующий сообщения между устройствами и платформой |
| Телеметрия | Периодические измерения состояния устройства |
| Событие | Сообщение о факте (переход порога, смена приложения на экране, загрузка устройства) |
| Проверка доступности (probe) | Периодический сетевой запрос агента к заданной цели (бэкенд, кухонная станция) с замером этапов: DNS, TCP, TLS, ответ |
| Эталонная цель | Заведомо надёжный внешний адрес; позволяет отличить «нет интернета» от «недоступен бэкенд» |
| Корреляция инцидентов | Объединение результатов проверок от многих устройств для определения причины и масштаба отказа |
| Тень устройства (Device Shadow) | Хранимое на сервере представление устройства: `desired` (желаемое), `reported` (фактическое), `delta` (расхождение) |
| Провижининг | Регистрация нового устройства и выдача ему учётных данных |
| LWT (Last Will and Testament) | Сообщение, публикуемое брокером при неожиданном разрыве соединения устройства |
| Retained-сообщение | Сообщение, сохраняемое брокером и доставляемое каждому новому подписчику топика |
| QoS | Уровень гарантии доставки MQTT: 0 — не более одного раза, 1 — минимум один раз, 2 — ровно один раз |
| Device Owner (DO) | Режим владельца устройства Android: расширенные права корпоративного приложения |
| К / П / Д | Этап реализации: **К**урсовая, **П**рактика, **Д**иплом (ВКР) |
| MVP (MVP-A / MVP-B) | Этап 0: проверка осуществимости до курсовой — на эмуляторах (A) и на реальных устройствах (B) |
| Outbox | Локальный (Room) персистентный буфер исходящих сообщений агента; запись удаляется после PUBACK брокера |
| `connId` | Идентификатор подключения, свежий на каждую попытку; одинаков в `online` и LWT одного подключения |
| Dynamic Security (DynSec) | Расширение Mosquitto: учётные записи, роли и ACL управляются на лету через `$CONTROL` |
| OQ-n | Открытый вопрос ТЗ, требующий решения автора (разд. 7.5) |

│       │                                                         │

### 5.2 Роли пользователей
| Роль | Права |
|---|---|
| Администратор | Всё: пользователи, правила тревог, провижининг, опасные команды (перезагрузка, обновление) |
| Инженер поддержки | Просмотр всех устройств, работа с тревогами и инцидентами, безопасные команды, правка параметров групп |
| Наблюдатель (менеджер ресторана/региона) | Просмотр устройств и тревог своих ресторанов |
| Устройство | Публикация в свои топики, подписка на свои топики и топик своего ресторана |

### 5.3 Режимы функционирования
- **Штатный** — устройства на связи, телеметрия поступает, тревоги обрабатываются.
- **Деградированный** — брокер/бэкенд RestoFleet недоступен: агенты буферизуют данные локально и досылают после восстановления.
- **Сервисный** — обновление компонентов; агенты переподключаются с экспоненциальной задержкой и случайным разбросом (jitter), исключая «лавину переподключений».

## 7. Протокол взаимодействия (MQTT)

### 7.1 Дерево топиков
Префикс `rf/v1/` (версионирование протокола).

| Топик | Направление | QoS | Retained | Назначение |
|---|---|---|---|---|
| `rf/v1/dev/{deviceId}/status` | устройство → (и LWT от брокера) | 1 | да | `online` / `offline` |
| `rf/v1/dev/{deviceId}/telemetry` | устройство → | 0 (досылка буфера — 1) | нет | Периодическая телеметрия |
| `rf/v1/dev/{deviceId}/probe` | устройство → | 0 (досылка буфера — 1) | нет | Результаты проверок доступности |
| `rf/v1/dev/{deviceId}/events` | устройство → | 1 | нет | События (в т.ч. смена состояния цели) |
| `rf/v1/dev/{deviceId}/shadow/reported` | устройство → | 1 | нет | Фактическое состояние |
| `rf/v1/dev/{deviceId}/shadow/desired` | → устройство | 1 | да | Желаемое состояние |
| `rf/v1/dev/{deviceId}/cmd/req` | → устройство | 1 | нет | Команды (с Message Expiry) |
| `rf/v1/dev/{deviceId}/cmd/res` | устройство → | 1 | нет | Результаты команд |
| `rf/v1/rest/{restaurantId}/broadcast` | → устройства ресторана | 1 | нет | Групповые сообщения/команды (Д) |

Подписки backend: `$share/backend/rf/v1/dev/+/{status|telemetry|probe|events|shadow/reported|cmd/res}`.
Консоль **не подключается к брокеру напрямую** — только через backend (REST + WebSocket).

Ответ на команду агент всегда публикует в собственный `cmd/res`; `Response Topic` допустим только равный ему (DynSec разрешает устройству лишь свои топики). `Correlation Data` возвращается без изменений (реш. 154). Нечитаемый `cmd/req`, пустой retained `desired` (очистка) и сообщение в чужой топик подтверждаются брокеру и отбрасываются (реш. 149).

### 7.2 Форматы сообщений (JSON, UTF-8)

**status** (он же LWT с `"state":"offline"`, `"reason":"lwt"`; `connId` в `online` и в LWT одного подключения совпадает, свежий на каждую попытку подключения — арх. P3):
```json
{ "state": "online", "ts": 1793865600000, "connId": "k-7f3a9c", "agentVersion": "1.0.0", "mode": "normal", "role": "kitchen", "bootId": "b7f2…",
  "device": { "model": "…", "manufacturer": "…", "osVersion": "16", "apiLevel": 36 } }
```
`role` — из учётной записи регистрации (ответ `/provision`); без неё поле опускается (v0.4). `mode` — режим работы (обычный / Device Owner). `bootId` — `/proc/sys/kernel/random/boot_id`, при недоступности — счётчик загрузок, иначе поле опускается. Штатная остановка агента: событие `agent_lifecycle`/`stop`, затем явный `offline` с `reason=stop` и тем же `connId` и штатный DISCONNECT (LWT не срабатывает); убийство процесса оставляет LWT с `reason=lwt` (реш. 150, 151); при смене учётной записи — `offline` с `reason=reconfigure` (v0.4).
Каноническая форма JSON: поля со значением `null` не передаются (`explicitNulls = false`), значения по умолчанию пишутся явно (реш. 15).

**telemetry** (пример для планшета кухни):
```json
{
  "ts": 1793865630000,
  "seq": 18234,
  "battery": { "level": 87, "charging": true, "plugged": "ac", "tempC": 38.4 },
  "thermal": { "status": "LIGHT", "headroom": 0.62 },
  "net": { "type": "wifi", "rssi": -67, "validated": true },
  "storage": { "freeMb": 5120 },
  "memory": { "availMb": 1430 },
  "uptimeSec": 360021,
  "foregroundApp": "com.android.chrome",
  "apps": [ { "pkg": "com.android.chrome", "versionName": "130.0", "versionCode": 0 } ]
}
```

**probe:**
```json
{
  "ts": 1793865630000,
  "results": [
    { "id": "api",  "ok": false, "error": "timeout", "totalMs": 5000, "dnsMs": 14, "connectMs": 38 },
    { "id": "kds",  "ok": true,  "status": 200, "totalMs": 212, "dnsMs": 9, "connectMs": 31, "tlsMs": 64, "ttfbMs": 108 },
    { "id": "ref",  "ok": true,  "status": 200, "totalMs": 95 }
  ]
}
```
Поля поэтапного времени (`dnsMs`, `connectMs`, `tlsMs`, `ttfbMs`) — с этапа К (FR-AG-33); `connectMs` — только TCP, без TLS. Значения `error`: `dns_fail`, `timeout`, `conn_refused`, `tls_error`, `http_4xx`, `http_5xx`, `no_network`, `local_network_denied`, `other`.

**events:**
```json
{ "ts": 1793865700000, "type": "probe_state", "target": "api", "state": "down", "error": "timeout", "failures": 3 }
```
Типы событий, описанные golden-фикстурами `docs/protocol/fixtures/`: `probe_state`, `net_changed`, `package_changed`, `agent_lifecycle` (`boot` / `start` / `stop`), `capability_check` (результат проверки из Capability Lab) и служебное `debug_seq` (только debug-сборка, сервер игнорирует). У событий идентификатора нет (см. 7.4). **v0.4:** `probe_state` — `target`, `state` (`up` / `down`), `error`, `failures`; `threshold` — `metric` (`battery_low`, `temp_high`, `thermal`), `state` (`enter` / `exit`), `value`, `limit` — вход в зону и выход с гистерезисом 2 % / 2 °C, для `thermal` порог — `SEVERE`; `fg_changed` — `from`, `to`; `fg_absent` — `pkg`, `sinceTs`, `limitMin`, `foregroundApp` (отслеживаемое приложение не на экране дольше `fgAbsentMin`).

**shadow/desired:**
```json
{
  "version": 12,
  "telemetry": { "intervalSec": 30 },
  "thresholds": { "batteryLowPct": 20, "tempHighC": 45, "fgAbsentMin": 10 },
  "watchedApps": ["com.android.chrome"],
  "probes": [
    { "id": "api", "type": "http", "url": "https://api.company.example/health", "intervalSec": 30, "timeoutMs": 5000, "failThreshold": 3 },
    { "id": "kds", "type": "http", "url": "https://kitchen.company.example/", "intervalSec": 60, "timeoutMs": 5000, "failThreshold": 3 },
    { "id": "ref", "type": "http", "url": "https://reference.example/", "intervalSec": 60, "timeoutMs": 5000, "failThreshold": 3, "reference": true }
  ]
}
```

Цель может содержать ожидаемый HTTP-код `expectedStatus`: без него проверка успешна при коде меньше 400, с ним — только при совпадении; `reference` по умолчанию `false` (v0.4). Допустимый диапазон `telemetry.intervalSec` — 10…3600 с. Версия старее сохранённой игнорируется, равная — только повторяет `reported`, новее — применяется и сохраняется.

**shadow/reported:** та же структура + `"appliedVersion": 12, "appliedAt": …, "errors": []`; QoS 1, `retain = false`. Агент применяет `thresholds` (события `threshold`, `fg_absent`) и возвращает применённые значения (v0.4). Коды в `errors`: `telemetryIntervalSec:out_of_range`, `probes:empty_id`, `probes:empty_url:<id>`, `probes:duplicate_id:<id>` (остаётся первая цель), `watchedApps:empty`, `watchedApps:invalid_name:<имя>` (реш. 134, 151, 161, 177).

**cmd/req** (MQTT 5 properties: `Response Topic = rf/v1/dev/{id}/cmd/res`, `Correlation Data = cmdId`, `Message Expiry Interval` = остаток срока жизни до `expiresAt`, по умолчанию 300 с — v0.4):
```json
{ "cmdId": "c-01J…", "type": "show_message", "params": { "text": "Перезагрузите роутер", "level": "warning" }, "expiresAt": 1793866100000 }
```
`expiresAt` — момент истечения (epoch, мс), равен моменту создания команды + срок жизни (по умолчанию 300 с, 1…86 400 с); Message Expiry Interval при публикации — остаток до `expiresAt` (арх. P2; v0.4). Допустимые `level`: `info`, `warning`, `critical` (реш. 89). Проверки параметров на стороне агента (`Capabilities.check`, реш. 91, 93, 94): `url` — только `https://` в нижнем регистре, не длиннее 2048 символов; имя пакета — не длиннее 255; `text` — не пустой и не длиннее 1000; `sha256` — ровно 64 hex-символа; длительность сигнала — 1…30 000 мс. Команда `install_update` несёт `package`, `url`, `sha256` (фикстура `cmd-req-install-update.json`).

**cmd/res:**
```json
{ "cmdId": "c-01J…", "status": "succeeded", "ts": 1793865800000, "result": {} }
```
Статусы: `received` (промежуточный, публикуется сразу при получении команды — арх. P1), затем один итоговый: `succeeded`, `failed`, `unsupported` (с полем `reason`, например `requires_device_owner`). `result` — JSON-объект **со строковыми значениями**; пустой успех — `{}`; у `received`, `failed`, `unsupported` поля `result` нет (реш. 123, 151). Коды `reason`, зафиксированные в MVP-A: `expired`, `timeout`, `invalid_params:<причина>`, `unknown_type:<тип>`, `exception:<Класс>`, `kiosk_active`, `package_not_watched`, `notifications_disabled`, `requires_device_owner` (реш. 135, 141, 143, 144). Порядок публикации: `received`, затем итог; итог `reboot` уходит через outbox (реш. 142).

### 7.3 Параметры сессии
- Keep Alive: 30 с (арх. P7); LWT на топик `status`, retained, QoS 1, свой `connId` на каждую попытку подключения.
- Clean Start = false, Session Expiry = 24 ч — команды для офлайн-устройства ждут в брокере.
- Client ID = `deviceId`, привязан к учётке (DynSec-клиент с `clientid = deviceId`, арх. P6); повторное подключение с тем же ID вытесняет старую сессию (брокер шлёт DISCONNECT `0x8E`, агент подключается снова через 5 мин + jitter до 1 мин — FR-AG-80).
- Подписки QoS 1 оформляются заново при каждом подключении. Входящие `cmd/req` и `desired` агент подтверждает брокеру вручную, после обработки (и после досылки итогов команд); при гибели процесса до подтверждения брокер передоставит сообщение, дубль команды отбросит журнал `cmdId` (реш. 149).
- Фоновая досылка буфера: пачки по 50, не быстрее 20 сообщений/с, порядок постановки; QoS публикации из буфера не ниже 1 (реш. 132, 133).

### 7.4 Правки протокола v0.3 (P1–P10)
Источник — `docs/architecture.md`, разд. 7; модели — `shared:protocol`, golden-фикстуры — `docs/protocol/fixtures/*.json`.

| # | Проблема в v0.2 | Правка |
|---|---|---|
| P1 | Статус `delivered` средствами MQTT не узнать | Агент сразу публикует `cmd/res` со `status: "received"`, затем итоговый |
| P2 | `expired` брокер молча не сообщает | Поле `expiresAt` в `cmd/req`; бэкенд переводит в `expired` по таймеру; поздний итоговый ответ побеждает. Агент не исполняет команду с истёкшим `expiresAt` (допуск часов 5 мин, v0.4) и отвечает `failed` / `expired` (реш. 11) |
| P3 | LWT старой сессии может прийти после нового `online` | `connId` в `online` и в LWT; чужой `connId` игнорируется |
| P4 | Shared subscription не получает retained | Источник истины статуса — БД |
| P5 | ACL `%u/#` позволяет устройству писать себе `desired`/`cmd/req` | Роль DynSec `device`: publish — `status, telemetry, probe, events, shadow/reported, cmd/res`; subscribe — `shadow/desired, cmd/req` |
| P6 | Client ID не привязан к учётке | DynSec-клиент с `clientid = deviceId` |
| P7 | R-01 «> 2 мин» против S2 «≤ 95 с» и NFR «≤ keepalive × 1,5 + 5 с» | Keepalive 30 с, R-01 сразу по LWT (grace настраивается, по умолчанию 0) ⇒ ≈ 50 с |
| P8 | Нет persistence брокера | `persistence true` + volume; очистка retained при выводе из эксплуатации |
| P9 | Аутентификация REST-polling не описана | HTTP Basic учёткой устройства; бэкенд хранит bcrypt-хэш пароля в `device_credentials` |
| P10 | Без ручного ack «без потерь QoS 1» не выполняется | Стабильный clientId, `Clean Start=false`, ack после commit пакета в БД |

Дополнения по итогам MVP-A:
- **Дедупликация (at-least-once).** Бэкенд обрабатывает `cmd/res` идемпотентно по паре `(cmdId, status)`. У событий идентификатора нет; при обрыве досылки буфера возможен одиночный дубль (запись удаляется после своего PUBACK). Телеметрия идёт QoS 0 (досылка буфера — QoS 1) и может теряться (реш. 133; M3-review).
- **Порядок.** Внутри `cmd/res` порядок `received` → итог сохраняется; при непустом буфере новое сообщение уходит в буфер, а не напрямую, чтобы не обогнать более раннее (реш. 132).
- **Расхождение часов.** `expiresAt` сверяется с часами устройства с допуском 5 мин (команда истекла, если `now > expiresAt + 5 мин`), Message Expiry брокера от часов не зависит (OQ-1, закрыт в v0.4).

### 7.5 Открытые вопросы (закрыты в v0.4)
| № | Вопрос | Варианты | Почему важно |
|---|---|---|---|
| OQ-1 | `expiresAt` сверяется с часами устройства: если часы планшета уходят вперёд больше чем на 5 мин, все команды получают `expired` | (а) допуск на рассинхронизацию в агенте; (б) опора только на Message Expiry брокера, `expiresAt` — информационный | Message Expiry от часов устройства не зависит (M3-review) |
| OQ-2 | У событий нет идентификатора, дубль после обрыва досылки неотличим от повторного события | (а) принять дубль как допустимый; (б) ввести `eventId` в события (правка протокола и фикстур) | Контракт дедупликации на бэкенде (M3-review) |

**v0.4:** OQ-1 закрыт вариантом (а) — допуск 5 мин в агенте, основная защита — Message Expiry брокера (реш. 206 этапа К, `docs/reports/1-coursework/decisions.md`); OQ-2 закрыт вариантом (а) — одиночный дубль события после обрыва досылки допустим, `eventId` не вводится (реш. 207 этапа К).

## 10. Ограничения платформы Android и режимы работы агента

### 10.1 Режимы
- **Обычный** — агент установлен как обычное приложение. Доступны телеметрия, проверки, события, тень, безопасные команды.
- **Владелец устройства (Device Owner)** — для корпоративных устройств. MDM на устройствах компании нет, поэтому конфликта с другой системой не будет, но установка DO на уже используемое устройство требует сброса до заводских настроек. На стенде включается командой (на эмуляторе без добавленных аккаунтов):
  ```
  adb shell dpm set-device-owner <пакет_агента>/.AdminReceiver
  ```
  Добавляет перезагрузку, тихую установку, режим киоска (в т.ч. для браузера с кухонной станцией), доступ к серийному номеру и аппаратным температурам.

### 10.3 Ограничения, выявленные в MVP-A
- Принудительная остановка агента (`force-stop`) не лечится сторожем (L3).
- `PACKAGE_USAGE_STATS` (Usage Access) выдаётся только вручную; политика DO его не выдаёт (D6).
- R13 (серийный номер) на API 29+ доступен только Device Owner с выданным `READ_PHONE_STATE`.
- Под киоском `show_message` и `launch_app` чужого пакета отвечают `failed` / `kiosk_active`.
- На API 26: `ApiLevelTooLow` для thermal status (R3) — правило R-03 опирается только на температуру батареи; Usage Access (R8) и геолокация (R5) — `PermissionMissing` без ручной выдачи; датчик `significant_motion` (R11) на эмуляторе отсутствует.
- Автозапуск после перезагрузки (L2) подтверждён на API 26 (`online` с новым `connId` через 1 с после `boot_completed`, без открытия UI) и на API 36 (журнал Lab).
- Ресурсы агента (RS1/RS2) в debug-сборке выше целей — ⚠️ (13.5).
- API 37 не проверен: эмулятор не запускается.

| Совместимость | Агент на эмуляторах API 26/29/31/33/35/36/37, режимы обычный/DO; при возможности — тестовые устройства компании (MVP-B) | К, П |

Сквозные сценарии приёмки:
1. **S1 Провижининг:** создать устройство в консоли → ввести код в агенте → устройство online в консоли.
2. **S2 Пропажа устройства:** выключить сеть эмулятора → статус `offline` по LWT ≈ 50 с (арх. P7), тревога R-01 ≤ 95 с → включить сеть → тревога закрыта автоматически, буфер дослан.
3. **S3 Перегрев:** сценарий симулятора «у плиты» → событие и тревога R-03 ≤ 5 с.
4. **S4 Параметры:** изменить интервал телеметрии в `desired` → агент применил → `delta` пуста.
5. **S5 Команда офлайн-устройству:** `show_message` выключенному устройству → доставка при подключении; команда с истёкшим сроком → `expired`.
6. **S6 Рабочее приложение закрыто:** свернуть браузер на «кухонном» эмуляторе → тревога R-04.
7. **S7 Недоступность цели:** Toxiproxy отключает цель «api» → R-05 на устройствах ≤ 100 с → восстановление → тревоги закрыты.
8. **S8 Классификация инцидентов (П):** сценарии симулятора — (а) глобальный отказ бэкенда → одна сводная тревога R-08; (б) отказ сети одного ресторана → R-07 только для него; (в) бэкенд недоступен из 2 ресторанов при доступной эталонной цели → R-09.
9. **S9 Режим владельца устройства (Д):** `reboot` в обычном режиме → `unsupported: requires_device_owner`; в режиме DO → перезагрузка; киоск с браузером.

В курсовой консоли и тревог нет, поэтому сценарии проверяются через Swagger UI и MQTT Explorer в сокращённом виде (`docs/stages/1-coursework.md`, разд. 7): **S1** — провижининг через Swagger → код в агенте → устройство `online` в `GET /devices`; **S2′** — выключить сеть эмулятора → статус `offline` ≈ 50 с → включить → буфер дослан; **S4**; **S5**; **S7′** — Toxiproxy отключает цель `api` → событие `probe_state: down` в БД. Сценарии S3, S6 и тревоги в S2/S7 — в практике.

### 13.2 Эксперимент «MQTT vs REST-polling» (курсовая)
- **Цель:** количественно обосновать выбор протокола.
- **Конфигурации:** N = 100 / 1 000 / 5 000 устройств; интервал телеметрии 30 с; интервал опроса команд в REST — 5 / 15 / 30 с.
- **Измеряемые величины:**
  1. трафик на устройство (байт/сутки, экстраполяция);

  5. поведение при деградации сети (Toxiproxy: 300 мс задержки, 5 % потерь).
- **Результат:** таблицы и графики в главе «Экспериментальная часть», выводы.

| Риск | Вероятность | Меры |
|---|---|---|
| Преподаватель не признаёт смартфоны/планшеты IoT-устройствами | Средняя | Согласовать формулировку темы заранее; акцент на IoT-паттернах (тени, LWT, телеметрия, распределённые проверки), встроенных датчиках, эмуляторах как цифровых двойниках |

- 1. Аналитическая часть — из отчёта по практике: предприятие, процессы «как есть», анализ инцидентов, обзор аналогов (MDM-системы, IoT-платформы, системы синтетического мониторинга), постановка задачи
- 2. Проектная часть — финальное ТЗ, архитектура, протокол, модель данных, классификатор инцидентов, безопасность, процессы «как будет»
- 3. Реализация — ядро из курсовой + подсистема из практики + расширения ВКР
- 4. Тестирование и апробация — сценарии S1–S9, нагрузка, эксперимент, апробация на виртуальном стенде
- 5. Экономическое обоснование — затраты на разработку и владение, оценка эффекта по экспертным оценкам с указанием допущений
- Заключение, источники, приложения (ТЗ, руководство пользователя, акт о тестировании — по согласованию с кафедрой)

### 16.7 Порядок работы с git
- `main` хранит документацию и завершённые этапы. Работа ведётся в ветке этапа: `stage/0-mvp`, `stage/1-coursework`, `stage/2-practice`, `stage/3-diploma`.
- Ветка этапа создаётся от `main` после слияния предыдущего этапа.
- По завершении этапа ветка сливается в `main` с `--no-ff` и получает тег: `mvp-a`, `mvp-b`, `coursework`, `practice`, `diploma`.
- Каждый этап заканчивается демонстрируемым результатом и зелёным CI (сборка, unit-тесты, Kover-гейт, detekt).
- Состояние этапа фиксируется в `docs/handoff.md` (обновляется после каждой задачи), отчёты вех — `docs/reports/<этап>/M<k>.md`, журнал решений — `docs/reports/<этап>/decisions.md`; это сырьё для текстов курсовой, практики и ВКР.
- Требования, получившие ❌ в матрице MVP, не реализуются ни на одном этапе.

## 17. Планы на развитие

### 17.1 Направления развития
Вне рамок курсовой, практики и ВКР; указываются в заключении ВКР как направления развития.

| Направление | Содержание |
|---|---|
| Метрики сервиса и брокера | Экспорт метрик backend и Mosquitto (`$SYS`) в Prometheus, дашборды Grafana, оповещения о состоянии самой платформы |
| Интеграция с СУ | Синхронизация справочника ресторанов и графиков работы, минимальных версий приложений; адаптер только на чтение |
| Уведомления | Push-уведомления о тревогах в Android-консоль в фоне, Telegram-бот, эскалация неподтверждённых тревог |
| Desktop-агент для Windows | Мониторинг ПК ресторанов и колл-центра (Kotlin/JVM + OSHI), общий модуль протокола с Android-агентом |
| Устройства курьеров | Мониторинг доступности бэкенда с устройств курьеров (BYOD — с согласием пользователя) |
| Встраиваемый SDK | Опциональная библиотека для приложений компании: сбои и ошибки запросов изнутри приложения |
| OTA-обновление агента | Централизованное обновление агента в режиме DO |
| Прогнозирование отказов | Анализ истории телеметрии (перегрев, деградация батареи) для прогнозирования отказов устройств |
| Отказоустойчивость | Кластер брокера, несколько экземпляров backend, резервирование БД |

### 17.2 Кандидаты в требования (не приняты, требуют решения)
Выявлены в MVP-A; в требования не включены, пока автор не примет решение.

| Кандидат | Содержание | Основание |
|---|---|---|
| Выход из киоска | Команда выхода из lock task (`setLockTaskPackages` без целевого пакета). Сейчас выход возможен только вне агента (`adb`, `am force-stop` цели) | прогресс MVP-A (M2); реш. 117, 141 |
| Восстановление киоска | Повторный вход в киоск после перезагрузки и после `install_update` целевого приложения; политика `setLockTaskFeatures(HOME \| NOTIFICATIONS)` | реш. 141 |
| Подписанный allowlist | Подпись списка `watchedApps` / `install_update`, чтобы компрометация сервера не позволяла ставить произвольные пакеты. Требование «пакет уже установлен» перед `install_update` не вводилось: первая установка отслеживаемого приложения — законный сценарий раскатки | реш. 143, 161; Ruling по ревью M2 |
| Применение `watchedApps` без перезапуска | Сейчас `package_changed` для пакетов, добавленных только через `desired`, начинает работать после перезапуска агента, версии приложений в телеметрии берутся из статического списка | реш. 161 |
| Доступ техника к DO-операциям в release | Сейчас операции по вводу пользователя (URL APK, пакет киоска) существуют только в debug | арх. разд. 12; реш. 140 |
| Замеры RS1/RS2 внутри агента | Строки Lab RS1/RS2 остаются `NOT_CHECKED`, замер идёт с хоста (`dumpsys meminfo`, статистика трафика по uid) | прогресс MVP-A (задача 3.7) |
| Разрешение на локальную сеть | Объявление разрешения и шаг мастера при переходе на `targetSdk 37` | реш. 2, 47, 59 |
| Wake lock на батарейных устройствах | Снять `PARTIAL_WAKE_LOCK`, если устройства работают от батареи (цена по батарее — MVP-B) | реш. 81 |

### 17.3 Требования, исключённые по итогам MVP (❌)
Правило: требование с ❌ в матрице MVP переносится сюда и не реализуется ни на одном этапе. По итогам MVP-A исключённых требований нет. Ресурсы агента в матрице — ⚠️, а не ❌ (Ruling контроллера 10.11.2026: предварительный замер не на целевой сборке (debug без R8, UI Lab; RS2 — счётчик wlan0 всего устройства), неосуществимость не доказана): RS1 (ОЗУ процесса: PSS ≈ 102 МБ против цели ≤ 60 МБ) и RS2 (трафик: ≈ 26,8 МБ за 400 с против цели ≈ 0,85 МБ/ч; вероятная причина — проба `apk` скачивает тестовый APK каждые 30 с). **Решение MVP-A:** цели RS1 (≤ 60 МБ) и RS2 (≤ 0,85 МБ/ч) в ТЗ сохраняются как целевые, но считаются непроверенными до замера release-сборки (R8) на реальном устройстве в MVP-B; повторный замер на desired v14 (маленькая проба, 60/60/60 с) дал PSS ≈ 102–105 МБ и ≈ 1,7 МБ/ч, то есть трафик вдвое выше цели даже без тяжёлой пробы — кандидаты: увеличить интервалы проб, переиспользовать TLS-соединения, сжатие телеметрии. Если release-замер не уложится, цели пересматриваются (ОЗУ — по факту, трафик — по числу целей) и фиксируются в ТЗ v0.4.
