> **Для новой сессии.** Прочитай `CLAUDE.md`, затем `docs/architecture.md` (разд. 1, 3–8, 12), затем этот файл. Состояние ядра — `docs/stages/1-coursework.md` (разд. 4, 8). Макеты: `docs/design/restofleet-blueprint.html#p`.

**Длительность:** ≈ 2 активных недели + анализ в компании по графику практики.
**Задание:** «Анализ инфраструктуры устройств ресторанов и инцидентов доступности серверной части; проектирование и реализация подсистемы проверок доступности и корреляции инцидентов».

---

## 1. Цель и результат

Главная причина обращений — «бэкенд не отвечает». Практика добавляет правила и тревоги, корреляцию проверок по ресторанам (устройство / сеть ресторана / бэкенд глобально / бэкенд локально) и Android-консоль для инженера поддержки. При глобальном отказе инженер видит **один инцидент**, а не сотню одинаковых тревог.

## 2. Входные условия

Курсовая закрыта: протокол стабилен, агент шлёт телеметрию/пробы/события, бэкенд принимает и хранит их, есть REST API с OpenAPI, dev-seed ресторанов, симулятор с профилями.

## 4. Архитектура этапа

### 4.1 Бэкенд: новые пакеты domain
| Пакет | Содержимое |
|---|---|
| alert | `Alert`, `AlertState (open → acknowledged → resolved)`, `RuleEngine` (R-01…R-06 — чистые функции над снимком состояния устройства), `Acknowledge/Resolve/ListAlerts`, дедупликация по `(rule, subject)` |
| incident | `ProbeAggregator` (окно 2 мин, шаг 30 с, по `ресторан × цель`), `IncidentClassifier` (таблица решений), `Incident`, подавление дочерних тревог (`parent_incident_id`), `ListIncidents/GetIncident` |
| realtime | порт `EventBus`; `server:api/ws` раздаёт события по WebSocket (статусы, телеметрия, тревоги, инциденты) |
| auth | `Login`, `RefreshToken` (JWT access 15 мин + refresh с ротацией) — для консоли |

### 4.2 Классификатор (чистая функция, пороги из конфига)
1. ≥ 50 % устройств ресторана offline **или** `ref` down со всех онлайн-устройств → **Сеть ресторана** (R-07).
2. Иначе: множество ресторанов `A`, где `api` down у ≥ P % онлайн-устройств при живом `ref`.
   - `|A| ≥ M` → **Бэкенд глобально** (R-08), один инцидент со списком `A`;
   - `0 < |A| < M` → **Бэкенд локально** (R-09) на каждый ресторан.
3. Одно устройство offline при живых соседях → **Устройство** (R-01).
4. Покрытые инцидентом R-01/R-05 получают `parent_incident_id` и не показываются в ленте отдельно.

Точность: симулятор в режиме `synthetic` пишет ground truth (`scenario, restaurant, expected_class, from, to`); скрипт сверяет с `GET /incidents` → матрица ошибок, цель ≥ 90 %.

### 4.3 Модель данных (новые миграции)
`alerts(id, rule_id, device_id, restaurant_id, state, severity, opened_at, ack_by, ack_at, resolved_at, resolved_by, comment, parent_incident_id)`, `incidents(id, kind, target, restaurants uuid[], started_at, resolved_at, evidence jsonb)`, `probe_agg_1m(restaurant_id, target, bucket, devices_online, devices_down, ref_down)`, `refresh_tokens(user_id, token_hash, expires_at, rotated_at)`.

### 4.4 Android-консоль
Модули (по `architecture.md` разд. 4): `console/core/{common, mvi, decompose, network, storage, designsystem, ui, testing}`, `console/root`, `console/app-android`, `console/app-desktop` (заглушка, собирается в CI), фичи `feature/<f>/{-domain, -data, -ui, -component}`:

| Фича | FR | Что на экране |
|---|---|---|
| auth | CN-01 | вход, сервер, хранение токенов в Keystore |
| dashboard | CN-02 | счётчики online/offline/тревоги, рестораны с проблемами (WS) |
| restaurants | CN-03 | список ресторанов → устройства ресторана (**только просмотр**) |
| devices | CN-04 | список с фильтрами (ресторан, роль, статус, версия), поиск; по умолчанию «Проблемы» |
| device-details | CN-05 | хост вкладок Состояние · Проверки (водопад фаз) · События · Тень + bottom sheet «Команда» |
| shadow | CN-06 | desired / reported / delta, правка desired |
| commands | CN-07 | отправка, статусы received/succeeded/expired |
| alerts | CN-08 | лента: подтвердить, закрыть с комментарием |
| provisioning | CN-09 | ресторан + роль + имя → код и TTL |
| incidents | CN-10 | переключатель «Тревоги | Инциденты», карточка с объяснением классификации |

Навигация: нижняя панель **Обзор · Устройства · Тревоги · Рестораны**; смартфон, одна панель. Стиль «операционный центр», две темы — токены из макетов в `core:designsystem`.

## 6. Тесты

Классификатор и правила — табличные тесты на каждый сценарий S8 и пограничные пороги. Консоль: domain ≥ 90 %, presentation ≥ 85 %, data ≥ 80 %. WS — интеграционный тест на `testApplication`.

## 7. Приёмка

- S1–S7 полностью из Android-консоли (S2, S3, S6, S7 — с тревогами).
- **S8:** (а) глобальный отказ бэкенда → одна сводная тревога R-08; (б) отказ сети одного ресторана → R-07 только для него; (в) бэкенд недоступен из 2 ресторанов при живом `ref` → R-09.
- Классификатор ≥ 90 % верных результатов на сценариях симулятора.
