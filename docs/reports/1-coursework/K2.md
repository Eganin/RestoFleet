## Что сделано в 2.2

**БД** (`server/data/.../db`, `V1__core.sql`): 12 таблиц по `1-coursework.md` 4.4 + `refresh_tokens`, `device_sessions`; PK `telemetry(device_id, ts)` и `probe_results(device_id, ts, target)` с `ON CONFLICT DO NOTHING` (реш. 205); индексы `devices(restaurant_id, role, status)`, `commands(device_id, status)`, частичные — для `ExpireCommands` и `MarkStalePollers`; CHECK на роли и статусы. Репозитории Exposed DSL, `ExposedTransactionRunner` (Failure → откат, повторов нет — реш. 233), HikariCP `READ COMMITTED`. Атомарность: погашение кода и refresh-токена, выдача команд REST-опросу — одним `UPDATE … RETURNING`; тень и команда — `SELECT … FOR UPDATE`.

**Ingest** (реш. 234, 235, 241, 242): одно соединение HiveMQ (`clientId` из конфига, `Clean Start=false`, Session Expiry 24 ч, Receive Maximum 1 000, ручной ack); shared-подписка `$share/backend/rf/v1/dev/+/{status,telemetry,probe,events,shadow/reported,cmd/res}`; `IngestPipeline` — пачка до 500 сообщений или 500 мс, **ack только после возврата use cases (commit)**; временный сбой БД — повтор той же пачки 1…30 с без ack, детерминированный — разбор по одному, «ядовитое» сообщение подтверждается и считается; нечитаемое — ack + счётчик `undecodable` + лог без payload. `DeviceMessageDecoder` отсекает то, что PostgreSQL отверг бы (NUL, время вне 1970–2100, заряд вне 0…100).

**Публикации и DynSec**: `HiveMqPublisher` — retained `desired` QoS 1 с `version`, очистка retained `desired` и `status` пустым payload, `cmd/req` с Response Topic, Correlation Data (`cmdId`), Message Expiry (остаток TTL); `DynSecBrokerAccounts` — `createClient` (сразу с ролью `device` и `clientid = deviceId`), `disableClient` (рвёт сессию), `deleteClient` через `$CONTROL/dynamic-security/v1`, ответ по `correlationData`, таймаут 5 с; «не найдено» при отключении и удалении — успех.

**Безопасность**: `BcryptHasher` (cost 10), `SecureRandomSecrets` (код — 128 бит base32 Крокфорда, 26 символов; пароль устройства и refresh — 32 байта base64url), `Sha256Digest`, `InMemoryDeviceCredentialCache` (TTL 5 мин, реш. 213); `SystemClock` и `UuidIdGenerator` — из `shared:kernel`. `toString` конфигов пароли маскирует (тест).

**Найденные и исправленные дефекты** (в коде первого исполнителя):
1. `HiveMqClient.publish` возвращал `"timeout"` на **каждую успешную** публикацию (успех и таймаут сливались в `null` через `?:`) — все публикации и команды DynSec считались отказом брокера. Поймано тестом DynSec.
2. `IngestPipeline.nextBatch` ждал хвост пачки через `withTimeoutOrNull { receive() }`: при таймауте ровно в момент приёма сообщение терялось — без обработки и без ack (держало слот Receive Maximum до переподключения). Теперь `select { onReceive; onTimeout }`, окно — по `TimeSource` (виртуальное время в тестах).
3. Kover: `createVariant("ci") {}` в JVM-модулях без `add("jvm")` — `server:domain` и `server:data` не входили в агрегированный гейт с 2.1.
4. detekt: 33 замечания (имена файлов, длина строк, число `return`) — исправлены без подавлений.

## Решения

229–240 — восстановлены по коду (разбиение вехи, учётка `backend`, роли вне `init-dynsec.sh`, тесты без TLS, транзакции без повторов, одно MQTT-соединение, политика сбоев ingest, атомарный провижининг, merge-patch `desired`, переходы команд, кража refresh-токена, идентификаторы и типы столбцов). ## Отклонения от плана

- `HiveMqIngest` как один класс не существует — разложен на 4 (реш. 242).
- Модуль `domainModule` (Koin для use cases) живёт в `server:data` (`di/Modules.kt`): domain не знает Koin, а `server:api` ещё нет. КМ2b оставил его там (реш. 251).
- Тестовый брокер — без TLS и с `backend` без привязки `clientid` (реш. 232, 243).
- `CheckHealth` собирается в `dataModule` (factory) из проб БД и брокера.

## Что не проверено

- TLS-соединение бэкенда с брокером (`MqttTls.trustOnly` проверен только на PEM) — на стенде в КМ2b/валидации.
- Учётка `backend` стенда проверена `mosquitto_sub` с `clientId` `backend` (подписка разрешена); публикация `desired`/`cmd/req` и `$CONTROL` этой учёткой на стенде — в КМ2b (`test-backend.sh`); в тестах те же ACL проверены живьём.
- Порядок «LWT после очистки retained `status`» при выводе из эксплуатации: если у агента Will Delay > 0, retained `status: offline` может появиться после очистки (повторный `DecommissionDevice` дочистит).
- Нагрузка ingest (5 000 устройств) — эксперимент КМ4.
- Ревью вехи не проводилось: одно ревью на этап после КМ4 (план).

## Контракт для КМ3 и КМ4

**Стенд и доступ.** Поднять: `cd deploy && ./prepare-stand.sh && docker compose --profile dev up -d --wait`. CA стенда — `deploy/certs/out/public/ca.crt` (SAN: `localhost`, `mosquitto`, `apk-host`, `backend`, `toxiproxy`, `127.0.0.1`, `10.0.2.2`, LAN-IP). Пароль `admin` — `deploy/out/admin-password` (600). Один экземпляр бэкенда (`clientId = backend`, реш. 230).

| Откуда | REST | MQTT |
|---|---|---|
| Эмулятор (агент, КМ3) | `https://10.0.2.2:8443/api/v1/…` (nginx, TLS, CA стенда) | `10.0.2.2:8883` (TLS) |
| Хост (симулятор КМ4 вне Docker) | `https://localhost:8443/api/v1/…` или напрямую `http://127.0.0.1:8080/api/v1/…` | `localhost:8883` |

| Через Toxiproxy (деградация) | `http://127.0.0.1:18080` (хост) / `http://toxiproxy:18080` (сеть compose) → `backend:8080` | `127.0.0.1:18883` / `toxiproxy:18883` → `mosquitto:8883` (TLS, SAN `toxiproxy`) |
| Цель проб агента (S7′) | `https://10.0.2.2:18443/health` → `apk-host:443` → `/health` | — |

**Провижининг агента (КМ3, FR-AG-10).** `POST https://10.0.2.2:8443/api/v1/provision`, `Content-Type: application/json`, без JWT, тело — `ProvisionRequestDto{code, deviceInfo{model ≤ 100, manufacturer ≤ 100, osVersion ≤ 32, apiLevel 1…1000}, agentVersion ≤ 64}` (регистр, пробелы и дефисы в коде не важны). Успех — **201** `ProvisionResponseDto{deviceId, password, restaurantId, role, mqtt{host: "10.0.2.2", port: 8883}}` (`Cache-Control: no-store`; пароль — один раз; `deviceId` = MQTT username и `clientId`; роль — из кода, реш. 210). Ошибки — тело `{code, message, field?, reason?}`: 400 `bad_request` / `validation` (`field`), **401 `token_invalid`**, **409 `token_used`**, **410 `token_expired`**, 429 `rate_limited` (`Retry-After`, 60/мин на IP), 503 `broker_unavailable` (повторить). После провижининга брокер держит retained `desired` v1; устройство `online` по своему `status`.

**Выпустить код (curl, с хоста):**

```bash
cd deploy
printf '{"login":"admin","password":"%s"}' "$(cat out/admin-password)" > /tmp/rf-login.json
curl -s --cacert certs/out/public/ca.crt -H 'Content-Type: application/json' --data-binary @/tmp/rf-login.json \
  https://localhost:8443/api/v1/auth/login \
  | python3 -I -c 'import json,sys; print("Authorization: Bearer "+json.load(sys.stdin)["accessToken"])' > /tmp/rf-auth
curl -s --cacert certs/out/public/ca.crt -H @/tmp/rf-auth https://localhost:8443/api/v1/restaurants   # id ресторанов (MSK-01…)
curl -s --cacert certs/out/public/ca.crt -H @/tmp/rf-auth -H 'Content-Type: application/json' \
  -d '{"restaurantId":"<id>","role":"kitchen","name":"Кухня-1"}' https://localhost:8443/api/v1/provisioning/tokens  # → code
```

**Симулятор (КМ4).** JWT: `POST /api/v1/auth/login {login: "admin", password}` → `accessToken` (15 мин) + `refreshToken` (`POST /api/v1/auth/refresh {refreshToken}`; одноразовый — после ротации старый недействителен, повтор погашенного отзывает **все** сессии admin). Пакет кодов: `POST /api/v1/provisioning/tokens:batch {restaurantId, role, name?, count 1…1000}` → 201 `{items: [{id, code, restaurantId, role, name, expiresAt}]}`. Перед массовой регистрацией поднять лимит: `RF_RATELIMIT_PROVISIONPERMINUTE=100000` в `deploy/.env` → `docker compose up -d backend`. Рестораны — `GET /api/v1/restaurants` (40 после seed). Команды эксперимента: `POST /api/v1/devices/{id}/commands {type: "ping", params: {}, ttlSec}` → 201 `CommandDto` (`cmdId`), статус — `GET /api/v1/commands/{cmdId}`. Время обнаружения пропажи — `GET /api/v1/devices/{id}` → `device.status = offline` (MQTT — по LWT; REST — без опроса дольше `RF_POLLING_STALEAFTERMS`, по умолчанию 90 с, проверка каждые 5 с).

**REST-polling (Basic `deviceId:password`).** `POST /api/v1/poll/telemetry` — тело `PollTelemetryRequestDto{telemetry, probe?, events[]}` (те же правила, что MQTT-ingest: NUL, `ts` вне 1970–2100, неизвестный тип события → 400 `invalid_payload` с `reason`), ответ **204**; опрос отмечает присутствие (`online`, транспорт `poll`). `GET /api/v1/poll/commands` → 200 `PollCommandsResponseDto{commands: [CommandRequestDto]}` — `queued` команды выдаются один раз и становятся `delivered`. `POST /api/v1/poll/commands/result` — тело `CommandResultDto` (как `cmd/res`), 204 (идемпотентно по `(cmdId, status)`), 404 — чужая или неизвестная команда. Неверная учётка — 401 `unauthorized`; кэш Basic — 5 мин.

**Toxiproxy.** Прокси `api` (18443 → `apk-host:443`), `mqtt` (18883 → `mosquitto:8883`), `rest` (18080 → `backend:8080`); управление — `http://127.0.0.1:8474` (с хоста): `GET /proxies`; выключить — `POST /proxies/<имя> {"enabled":false}`; задержка — `POST /proxies/<имя>/toxics {"name":"lat300","type":"latency","stream":"downstream","attributes":{"latency":300}}`, снять — `DELETE /proxies/<имя>/toxics/lat300`; всё вернуть — `POST /reset`. Конфигурация из `deploy/toxiproxy.json` — при старте контейнера. Потери 5 % — `tc netem` в контейнере симулятора (план 4.3), Toxiproxy их не делает.
