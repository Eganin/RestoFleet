## Что сделано в 2.2

**БД** (`server/data/.../db`, `V1__core.sql`): 12 таблиц по `1-coursework.md` 4.4 + `refresh_tokens`, `device_sessions`; PK `telemetry(device_id, ts)` и `probe_results(device_id, ts, target)` с `ON CONFLICT DO NOTHING` (реш. 205); индексы `devices(restaurant_id, role, status)`, `commands(device_id, status)`, частичные — для `ExpireCommands` и `MarkStalePollers`; CHECK на роли и статусы. Репозитории Exposed DSL, `ExposedTransactionRunner` (Failure → откат, повторов нет — реш. 233), HikariCP `READ COMMITTED`. Атомарность: погашение кода и refresh-токена, выдача команд REST-опросу — одним `UPDATE … RETURNING`; тень и команда — `SELECT … FOR UPDATE`.

**Ingest** (реш. 234, 235, 241, 242): одно соединение HiveMQ (`clientId` из конфига, `Clean Start=false`, Session Expiry 24 ч, Receive Maximum 1 000, ручной ack); shared-подписка `$share/backend/rf/v1/dev/+/{status,telemetry,probe,events,shadow/reported,cmd/res}`; `IngestPipeline` — пачка до 500 сообщений или 500 мс, **ack только после возврата use cases (commit)**; временный сбой БД — повтор той же пачки 1…30 с без ack, детерминированный — разбор по одному, «ядовитое» сообщение подтверждается и считается; нечитаемое — ack + счётчик `undecodable` + лог без payload. `DeviceMessageDecoder` отсекает то, что PostgreSQL отверг бы (NUL, время вне 1970–2100, заряд вне 0…100).

**Публикации и DynSec**: `HiveMqPublisher` — retained `desired` QoS 1 с `version`, очистка retained `desired` и `status` пустым payload, `cmd/req` с Response Topic, Correlation Data (`cmdId`), Message Expiry (остаток TTL); `DynSecBrokerAccounts` — `createClient` (сразу с ролью `device` и `clientid = deviceId`), `disableClient` (рвёт сессию), `deleteClient` через `$CONTROL/dynamic-security/v1`, ответ по `correlationData`, таймаут 5 с; «не найдено» при отключении и удалении — успех.

**Безопасность**: `BcryptHasher` (cost 10), `SecureRandomSecrets` (код — 128 бит base32 Крокфорда, 26 символов; пароль устройства и refresh — 32 байта base64url), `Sha256Digest`, `InMemoryDeviceCredentialCache` (TTL 5 мин, реш. 213); `SystemClock` и `UuidIdGenerator` — из `shared:kernel`. `toString` конфигов пароли маскирует (тест).

**Найденные и исправленные дефекты** (в коде первого исполнителя):
1. `HiveMqClient.publish` возвращал `"timeout"` на **каждую успешную** публикацию (успех и таймаут сливались в `null` через `?:`) — все публикации и команды DynSec считались отказом брокера. Поймано тестом DynSec.
2. `IngestPipeline.nextBatch` ждал хвост пачки через `withTimeoutOrNull { receive() }`: при таймауте ровно в момент приёма сообщение терялось — без обработки и без ack (держало слот Receive Maximum до переподключения). Теперь `select { onReceive; onTimeout }`, окно — по `TimeSource` (виртуальное время в тестах).
3. Kover: `createVariant("ci") {}` в JVM-модулях без `add("jvm")` — `server:domain` и `server:data` не входили в агрегированный гейт с 2.1.
4. detekt: 33 замечания (имена файлов, длина строк, число `return`) — исправлены без подавлений.

## Решения

229–240 — восстановлены по коду (разбиение вехи, учётка `backend`, роли вне `init-dynsec.sh`, тесты без TLS, транзакции без повторов, одно MQTT-соединение, политика сбоев ingest, атомарный провижининг, merge-patch `desired`, переходы команд, кража refresh-токена, идентификаторы и типы столбцов). Новые: 241 (защита ingest от сообщений, которые отвергнет PostgreSQL), 242 (`HiveMqIngest` = `HiveMqClient` + `IngestPipeline` + `IngestProcessor` + `MqttBackend`), 243 (отличия тестового брокера: `backend` без `clientid`, очистка сессий, контейнер на JVM).

## Отклонения от плана

- `HiveMqIngest` как один класс не существует — разложен на 4 (реш. 242).
- Модуль `domainModule` (Koin для use cases) живёт в `server:data` (`di/Modules.kt`): domain не знает Koin, а `server:api` ещё нет. КМ2b может перенести его в `server:app`.
- Тестовый брокер — без TLS и с `backend` без привязки `clientid` (реш. 232, 243).
- `CheckHealth` собирается в `dataModule` (factory) из проб БД и брокера.

## Что не проверено

- TLS-соединение бэкенда с брокером (`MqttTls.trustOnly` проверен только на PEM) — на стенде в КМ2b/валидации.
- Учётка `backend` стенда проверена `mosquitto_sub` с `clientId` `backend` (подписка разрешена); публикация `desired`/`cmd/req` и `$CONTROL` этой учёткой на стенде — в КМ2b (`test-backend.sh`); в тестах те же ACL проверены живьём.
- Порядок «LWT после очистки retained `status`» при выводе из эксплуатации: если у агента Will Delay > 0, retained `status: offline` может появиться после очистки (повторный `DecommissionDevice` дочистит).
- Нагрузка ingest (5 000 устройств) — эксперимент КМ4.
- Ревью вехи не проводилось: одно ревью на этап после КМ4 (план).

## Контракт для КМ2b

**Koin.** `server:app` ставит `modules(appModule, dataModule, domainModule, apiModule)`; оба модуля — `ru.restofleet.server.data.di`.
- `dataModule` требует **`DataConfig`**. Даёт: `Clock` (`SystemClock`), `IdGenerator` (`UuidIdGenerator`), `HikariDataSource`/`DataSource` (закрывается при `koin.close()`), `Database`, `TransactionRunner`, все репозитории, `PasswordHasher`, `SecretGenerator`, `SecretDigest`, `DeviceCredentialCache`, `HiveMqClient`, `MessagePublisher`, `BrokerAccounts`, `IngestMetrics`, `DeviceMessageDecoder`, `InboundProcessor`, `IngestPipeline`, `MqttBackend`, `DatabaseHealthProbe`, `BrokerHealthProbe`, `CheckHealth` (factory).
- `domainModule` — 29 use cases (factory) + `SessionIssuer` (single); требует от `server:app`: **`ProvisioningSettings(broker: BrokerEndpoint(host, port), tokenTtlMillis = 24 ч)`** (адрес брокера для агента: стенд — `10.0.2.2:8883`), **`PollingSettings(staleAfterMillis = 90 000)`**, **`AuthSettings(refreshTtlMillis = 7 сут)`**, **`AccessTokenIssuer`** (`fun interface`: `issue(user): AccessToken(token, expiresAt)` — JWT 15 мин, подпись — api/app).
- Проверка графа — `server/data/src/test/.../di/ModulesTest` (каждый use case создаётся); образец сборки — `support/KoinBackend.kt`.

**Конфиг `DataConfig`** (`ru.restofleet.server.data.config`):
- `database = DatabaseConfig(jdbcUrl, user, password, maxPoolSize = 10, connectionTimeoutMs = 5 000)`;
- `mqtt = MqttConfig(host, port, username = "backend", password, clientId = "backend", caFile: String? = null, keepAliveSec = 30, sessionExpirySec = 86 400, receiveMaximum = 1 000, requestTimeoutMs = 5 000, publishTimeoutMs = 10 000)` — на стенде `host = mosquitto`, `port = 8883`, `caFile = /certs/ca.crt` (CA стенда, `certs/out/public/ca.crt`), пароль — из `deploy/out/backend-mqtt-password` (файл/секрет, не env в compose-файле и не argv); `caFile = null` (без TLS) — **только тесты** (реш. 232);
- `ingest = IngestConfig(batchSize = 500, batchWindowMs = 500, retryInitialMs = 1 000, retryMaxMs = 30 000, maxPayloadBytes = 256 КБ)`;
- `deviceAuthCacheTtlMs = 300 000`.
- `toString` всех трёх пароли маскирует — конфиг можно логировать.

**CLI `migrate`**: `Migrations.migrate(dataSource): Int` (число применённых, Flyway `classpath:db/migration`). `serve` миграции сам не делает (решать в КМ2b; на тестах — `TestDatabase`).

**Ingest и MQTT** (реш. 242): при старте `get<MqttBackend>().start(appScope)` (подключается с повторами, подписывается, запускает конвейер; возвращает `Job`), при желании `awaitReady()`; отказ брокера в подписке — исключение в этой задаче → завершить процесс. При остановке — `stop()` (неподтверждённая пачка останется у брокера и придёт снова), затем `koin.close()` (Hikari). `isReady` = подписан и подключён. Только **один** экземпляр бэкенда с `clientId = backend` (второй вытеснит первый, реш. 230, 243). `IngestMetrics.snapshot()` — счётчики для лога/`/health`.

**Фоновые задачи — запускает `server:app`** (в КМ2a их нет): `ExpireCommands()` каждые 5 с (возвращает число истёкших), `MarkStalePollers()` каждые 5 с (реш. 214). Обе — короткие транзакции, ошибки ловить и логировать, цикл не ронять.

**Use cases** (все `suspend operator fun invoke`; ошибки — `Outcome<_, ServerError>` с полем `code`: `NotFound`, `Conflict`, `Validation(field, reason)`, `Unauthorized`, `TokenInvalid`, `TokenExpired`, `TokenUsed`, `DeviceDecommissioned`, `BrokerUnavailable(operation)`; HTTP-коды по KDoc `ServerError` — 404/409/400/401/401 или 404/410/409/410/503, окончательно решает api; сбой БД — исключение мимо `Outcome` → 500/503):
- рестораны: `CreateRestaurant(RestaurantDraft)`, `UpdateRestaurant(RestaurantId, RestaurantPatch)`, `GetRestaurant(RestaurantId)` → `Outcome<Restaurant, ServerError>`; `ListRestaurants()` → `List<Restaurant>`; `UpsertRestaurantByCode(RestaurantDraft)` → `Outcome<UpsertedRestaurant, …>` (seed);
- устройства: `ListDevices(DeviceFilter, PageRequest = of())` → `List<Device>`; `GetDevice(DeviceId)` → `Outcome<DeviceDetails(device, lastTelemetry, lastSession), …>`; `DecommissionDevice(DeviceId)` → `Outcome<DecommissionResult(device, retainedCleared), …>`;
- провижининг: `IssueProvisioningTokens(IssueTokensRequest(restaurantId, role, name?, count 1..1000))` → `Outcome<List<IssuedToken>, …>` (код — один раз); `ProvisionDevice(ProvisionRequest(code, DeviceInfo, agentVersion))` → `Outcome<ProvisionedDevice(deviceId, password, restaurantId, role, broker), …>`;
- история: `GetTelemetryHistory(id, TimeRange, page)`, `GetProbeHistory(id, range, target?, page)`, `GetEventHistory(id, range, type?, page)` → `Outcome<List<…>, …>` (новые сначала, `[from, to)`);
- тень: `GetShadow(DeviceId)` → `Outcome<Shadow, …>` (`delta`, `isPending`); `UpdateDesired(DeviceId, ShadowDocument)` → `Outcome<UpdatedShadow(shadow, published), …>` (merge-patch, реш. 237; JSON ↔ `ShadowDocument` — `ShadowJson` из `server:data` или свой маппер api);
- команды: `SendCommand(CommandRequest(deviceId, type, params, ttlSec = 300))` → `Outcome<Command, …>`; `GetCommand(cmdId)`; `HandleCommandResult(CommandReport)` → `IngestOutcome`; `ExpireCommands()` → `Int`;
- polling (реш. 213, 214): `AuthenticateDevice(username, password)` → `Outcome<DeviceId, …>`; `PollTelemetry(DeviceId, DeviceDataBatch)` → `IngestResult`; `PollCommands(DeviceId)` → `List<Command>`; `MarkStalePollers()` → `Int`; REST DTO → домен: `DeviceMessageDecoder` работает с топиками MQTT, для REST нужен свой маппер DTO (те же правила, реш. 241);
- auth: `Login(login, password)`, `RefreshSession(refreshToken)` → `Outcome<SessionTokens, …>`; `UpsertUser(login, password)` → `Outcome<User, …>` (seed admin);
- `CheckHealth()` → `HealthReport(components = {database, broker})`; ingest-обработчики `HandleStatus`, `IngestBatch`, `HandleReported` вызывает только `IngestProcessor`.
