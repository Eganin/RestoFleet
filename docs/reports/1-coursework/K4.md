## Что сделано

### 4.1 `server:simulator` (FR-SM-01…03, 06, 07, базовый 08; реш. 279, 285, 286, 288)
- **domain** (без фреймворков и протокола, правило Konsist): профили `KitchenProfile` (на зарядке, нагрев у плиты в часы пик 12–15 и 18–21 до 40 °C + индивидуальная добавка 0…5 °C), `HallProfile` (смена 10–23: разряд ≈ 6 %/ч, после — зарядка), `AssemblyProfile` (15 мин из 45 — в доке) — чистые генераторы от `Random(seed + i)`, суточное время с ускорением `timeScale`; `VirtualDevice` — поведение агента: телеметрия по профилю, пороги (`ThresholdTracker`, правила реш. 264), тень (`VersionDecision`, `validateDesired` из `shared:shadow`), команды (идемпотентно по `cmdId`, `received` + итог, допуск часов 5 мин — реш. 206; `ping`, `show_message`, `launch_app`, `run_probe`, `collect_diagnostics` как у агента, DO-команды — `unsupported`), пробы (`ProbeStateMachine`, `ProbeSchedule.forStand()`); `DeviceRunner` — циклы устройства поверх порта `DeviceLink`; `DevicePlan` — раскладка 2/3/1 по ресторанам; use cases `RegisterDevices` и `RunExperiment`.
- **data**: `MqttDeviceConnector`/`MqttDeviceLink` — клиент HiveMQ на устройство, общий Netty event loop, TLS с доверием только CA стенда, LWT `status offline` с `connId`, `Clean Start = false`, Session Expiry 24 ч, keep-alive 30 с, автопереподключение 1…120 с своим CONNECT (урок реш. 259), QoS как у агента; `BlackholeRelay` — «тихая» пропажа; `PollingDeviceConnector` — REST-polling (Basic, keep-alive на устройство); `OkHttpControlApi` (admin JWT, повторный вход по 401), `OkHttpProvisioningApi`; `JsonlCredentialStore` (600); `YamlScenarioLoader` (kaml, строгий); `CsvResultSink`; `InterfaceTrafficMeter`; `HttpProbeRunner` (HTTP/TCP, классы ошибок `shared:probes`). Сообщения — только DTO и топики `shared:protocol` (`ProtocolMapper`, `InboundMapper`, проверка по golden-фикстурам).
- **app**: CLI `register | run | experiment`, Koin только здесь.
- **Сборка и стенд:** модуль в Kover-агрегаторе (`kover(projects.server.simulator)`, вариант `ci` — `add("jvm")`) и в Konsist (реш. 279); `server/simulator/Dockerfile` (JRE 21 + iproute2), сервис `simulator` в compose (profile `experiment`, `cpus`/`mem_limit`, `cap_add: NET_ADMIN, SETUID, SETGID`, `read_only`, `no-new-privileges`), сеть `control`.

### 4.2 Измеритель (реш. 280–284, 287, 289, 290)
- `RunExperiment`: разгон с jitter → прогрев → окно (снимки счётчиков и байт интерфейса на границах) → команды `ping` k/мин случайным устройствам через REST API (admin) → добор и итоговые статусы → пропажа K устройств и опрос `GET /devices/{id}` до `offline` → штатная остановка; временной ряд раз в 5 с.
- Задержка команды: `System.nanoTime` перед `POST /devices/{id}/commands` и в колбэке HiveMQ/ответе опроса — один процесс, одни часы; p50/p95 — ближайший ранг.
- Трафик: счётчики интерфейса устройств в контейнере (измеритель — по отдельной сети `control`), сверка — NET I/O `docker stats`.
- CPU/ОЗУ: `tools/experiments/sample_docker_stats.py` на хосте, раз в 5 с → `docker-stats.csv`.
- Оркестратор `tools/experiments/run-experiment.sh` (`build`, `register N`, `run <сценарий>`, `restore`), сценарии — `tools/experiments/scenarios/*.yaml` (16 прогонов эксперимента + 2 smoke).

## Решения

Rulings 279–290 — `decisions.md`, раздел «КМ4»: 279 слои симулятора пакетами и правила Konsist; 280 трафик по счётчикам интерфейса и отдельная сеть `control` для измерителя; 281 REST-устройство шлёт только итог команды, тени в REST нет; 282 REST по HTTP без TLS (консервативно в пользу REST); 283 «тихая» пропажа через реле и порог presence REST = 3 × опрос; 284 деградация: Toxiproxy +300 мс downstream и `netem loss 5%` на uplink, только N = 1 000, MQTT и REST 15 с; 285 остановка с Session Expiry 0; 286 один кэш учёток и раскладка по кругу; 287 параметры прогона; 288 ресурсы контейнера симулятора; 289 настройки бэкенда — через окружение команды, без правки `.env`; 290 сэмплер `docker stats` на хосте.

## Отклонения от плана

- **Кэш учёток** — один файл `deploy/out/sim/creds.jsonl` (JSON Lines) вместо `sim-creds-<run>.json`: регистрация 5 000 один раз на все прогоны (реш. 286).
- **REST — без TLS** (HTTP прямо к бэкенду, как в контракте K2), MQTT — с TLS: план транспорт REST не задавал (реш. 282).
- **Деградация** — только MQTT и REST 15 с (не все интервалы), latency и потери раздельно (реш. 284).
- **Пробы в эксперименте не участвуют:** тень по умолчанию без целей (`DefaultDesired`), поэтому прогоны пробы не запускали; совпадение поведения с агентом (`probe`, `probe_state`, `run_probe`, `collect_diagnostics`) проверено тестами (`VirtualDeviceTest`, `DeviceRunnerTest`, `RestClientsTest`, Testcontainers `MqttDeviceLinkTest`).
- **Режим проверок `synthetic`** (ground truth, арх. разд. 10) и сценарии отказов FR-SM-04/05 — этап П, не делались.

## Что не проверено

- **Суточный прогон** — нет (реш. 209): окно 240 с, «в сутки» — экстраполяция; переподключения за сутки, ротация JWT измерителя дольше 15 мин, рост БД — не измерены.
- **10 000 устройств** — не пробовали (Д); 5 000 — см. «Прогоны».
- **REST через HTTPS** (nginx) — не мерился (реш. 282).

- **Пробы виртуальных устройств против целей стенда** (`api` через Toxiproxy) — только тесты; в прогонах целей нет.
- **Симулятор вне Docker** (с хоста): запускается, но трафик не меряется (нет `/sys/class/net`), под нагрузкой не проверялся.

Трафик на устройство от N почти не зависит (MQTT 2,64 → 2,56 МБ/сутки при 1 000 → 5 000), нагрузка на сервер у REST растёт с N и частотой опроса намного быстрее, чем у MQTT (при N = 5 000 — в 10,1 раза по среднему, в 6,9 раза по медиане против REST 5 с).

- **Особенность MQTT-пропажи:** Mosquitto 2.1 проверяет keep-alive пачками (9 из 10 пропавших отключены в одну миллисекунду), поэтому разброс по прогонам разный: 19,8…40,3 с при N = 1 000, 43,4…44,4 с при N = 100, 44,5…45,6 с при N = 5 000; верхняя граница — ≈ 1,5 × keep-alive (45 с).
- **Всплески CPU REST при N = 5 000** (`img/timeline-5000.png`): bcrypt-проверки Basic при первой аутентификации (разгон) и через 5 мин, когда истекает кэш (реш. 213) — второй всплеск попадает в последние ≈ 20 с окна; поэтому в таблицах есть и медиана CPU.

**Чем выводы отличаются качественно.** В серии 1 нагрузка REST на сервер «росла с N и частотой опроса», а превосходство MQTT по CPU при N = 5 000 (10,1 раза) держалось на всплеске в конце окна. В серии 2: (1) CPU REST в 5–17 раз выше MQTT уже при N ≥ 1 000 при любом интервале опроса (в серии 1 при N = 1 000 — 2,8–4,0 раза); (2) при N ≥ 1 000 средний CPU REST определяют периодические проверки bcrypt раз в TTL кэша Basic на устройство, а не частота опроса — редкий опрос (30 с) почти не дешевле частого (5 с) по среднему; частоту опроса видно по медиане; (3) синхронный всплеск bcrypt после массового подключения задерживает и команды REST (13 из 600 при N = 5 000 сверх интервала). Выводы о трафике (MQTT в 1,6–5,7 раза меньше), задержке (миллисекунды против ½ интервала) и обнаружении пропажи (MQTT ≤ 1,5 × keep-alive, REST ≈ 3 × опрос) не изменились.
