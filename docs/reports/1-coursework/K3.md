## Что сделано

### 3.1 `ApplyShadow` на `shared:shadow`, `expectedStatus` (реш. 219)
`ApplyDesiredShadow` уже в КМ1 брал решение по версии и валидацию из `shared:shadow` (`VersionDecision`, `validateDesired`, реш. 225) — проверено, поведение и тесты MVP не менялись. Сквозь весь путь проведено `ProbeTargetDto.expectedStatus`: доменная `ProbeTarget.expectedStatus`, `ShadowMapper` (desired → domain), `JsonPayloadEncoder.reported` (эхо в `reported`; тест по фикстуре `shadow-desired-expected-status`: `version`, `telemetry`, `thresholds`, `watchedApps`, `probes` в `reported` равны `desired` — `delta` пуста), `FileShadowStore` (поле с умолчанием: файл тени MVP читается), `OkHttpProbeExecutor` → `classifyHttpStatus(code, expected)`. KDoc `DesiredShadow` исправлен: пороги проверяет агент (реш. 202).

### 3.2 `RunProbes` + `probe_state` (FR-AG-34, 35, 44; реш. 226, 228, 263)
Use case `RunProbes` (domain): цели вызова проверяются параллельно, итог каждой учитывает автомат `ProbeStateMachine` из `shared:probes` (`ProbeStates` — по автомату на `id`), на каждый переход (в том числе `UNKNOWN → UP`) сразу уходит `probe_state {target, state, error, failures}`, затем отчёт `probe`. Без связи оба сообщения — в outbox (FR-AG-35, через `PublishOrBuffer`). `ProbeLoop` (data) — только расписание: интервал цели, но не чаще `ProbeSchedule` (debug — 5 с, стенд; release — 30 с). Псевдоним `ProbeError` оставлен (переименование по всему агенту — без пользы для К).

### 3.3 `EvaluateThresholds` (FR-AG-40, 41; реш. 202, 218, 220, 264, 265)
Use case `EvaluateThresholds` вызывается тиком телеметрии после публикации снимка (`TelemetryTick`, сбой изолирован). Пороги и отслеживаемые приложения — из применённой тени (без тени — значения по умолчанию). `ThresholdTracker` — вход/выход из зоны с гистерезисом (`battery_low` ≤ порог / ≥ порог + 2; `temp_high` ≥ порог / ≤ порог − 2; `thermal` от `SEVERE`), `ForegroundTracker` — `fg_changed` на каждую смену (первое наблюдение — точка отсчёта), `fg_absent` один раз на эпизод отсутствия дольше `fgAbsentMin`. Состояние — в памяти (оговорка плана).

### 3.4 Досылка, дедупликация, часы (реш. 203, 204, 206, 266, 267)
- `FlushTrigger` (порт domain) → `ConflatedFlushTrigger` (data): сообщение легло в outbox при живой связи — `SessionSupervisor` досылает сразу; таймер 60 с остался страховкой. Наблюдение 11.11 (события ждали до 60 с) закрыто.
- `PublishPackageChange`: одинаковое `(pkg, change, versionCode)` в окне 5 с от последней отправки отбрасывается; `EventPump` шлёт пакеты через него.
- `HandleIncomingCommand`: команда истекла, только если `now > expiresAt + 5 мин` (OQ-1, вариант (а)).

### Команды `run_probe{target}`, `collect_diagnostics{}` (FR-AG-62, 64; реш. 221, 268)
`CommandMapper` их разбирает (тест: ни один тип `CommandTypes` не отвечает `unknown_type`), `Capabilities.check` проверяет `target`, `ExecuteCommand` отдаёт их порту `OnDemandChecks`; реализация `DiagnosticsCommands` (domain) идёт через `RunProbes` (тот же автомат) и `CollectTelemetry` + `PublishTelemetry`. `result` — только строки.

### 3.5 `Provision` (FR-AG-10, 12; реш. 210, 269–273)
- Domain: порт `ProvisioningApi`, модель `ProvisionedDevice`/`Registration`/`RegistrationState`, `DeviceRole`, ошибки `ProvisionError`; use cases `Provision` (адрес `https://хост[:порт]`, код, погашение, сохранение учётки с ролью и рестораном) и `GetRegistration`.
- Data: `OkHttpProvisioningApi` (`POST {baseUrl}/api/v1/provision`, DTO `shared.protocol.rest`, проверка ответа 201, классы ошибок по `code` бэкенда и по сети, без повторов и редиректов), `ProvisioningTrust` (debug — пиннинг CA стенда через `CaTrust`, как MQTT; release — системное доверие), `provisioningModule`. Учётка — `KeystoreCredentialStore`, запись версии 2 (роль, ресторан; версия 1 MVP читается).
- App: debug-интент `DEV_PROVISION` (тот же `DevConfigReceiver`, `DUMP`), `verifyReleaseNoDebugSurface` проверяет отсутствие действия в release.

### 3.6 Мастер и экран статуса (FR-AG-04 базово, FR-AG-05; реш. 274–278)
MVI по канону (`BaseMviViewModel`, Session/Intent/Action/Reducer/UiState/Mapper, Screen без ViewModel, Container, `view/section`, `api/I<F>Router`):
- `root` — навигация: `LOADING` → `SETUP` (нет учётки) или `STATUS` (есть или Keystore временно недоступен), `LAB` (только debug) с возвратом туда, откуда открыли;
- `setup` — мастер: разрешения (уведомления, usage access, батарея; кнопки системных настроек, перечитываются при возврате) → адрес стенда (по умолчанию `https://10.0.2.2:8443`) и код → `Provision` → итог (устройство, роль, ресторан) → статус;
- `status` — подключение (состояние, причина ошибки, `connId`, брокер), устройство (регистрация, режим normal/DO, размер outbox, версия), разрешения, пробы (up/down, HTTP-код и время или ошибка, неудач подряд); снимок `GetAgentStatus` раз в 3 с, пока экран виден.
- App: `AgentRouter` (переходы — намерения `RootViewModel`, настройки — контекст приложения), `MainActivity` собирает экраны; Capability Lab с вкладкой Device Owner — `LabScreen` только в debug (реш. 275).

### 3.7 `status.role` (реш. 210, 271)
`StatusPayloads.online(connId, ts, role)`; роль берётся из сохранённой учётки при каждом `online` (тест — по фикстуре `status-online` целиком, с `role`). У учётки `DEV_CONFIG` роли нет — поле опускается.

## Отклонения от плана

- **Один кодовый коммит вместо коммитов по подзадачам.** Гейт (≈ 7 мин) гонялся на полном дереве КМ3; дробить уже проверенное дерево на непроверенные промежуточные коммиты правило «гейт перед каждым коммитом» не позволяет.
- **Capability Lab — только debug** (реш. 275): в MVP release показывал Lab без команд; теперь release — только мастер и статус. Кнопка Lab есть и в мастере, не только в статусе (отладочному устройству без учётки Lab тоже нужен).
- **`DEV_PROVISION` — второе действие `DevConfigReceiver`**, а не отдельный ресивер (реш. 273).
- **Пороги** (реш. 264, 265) и **досылка по сигналу** (реш. 266) уточнены Rulings: границы гистерезиса, начало эпизода `fg_absent`, когда сигналить.
- **Псевдоним `ProbeError`** оставлен (K1 разрешал убрать) — переименование по всему агенту для К ничего не даёт.
- **Отслеживаемые пакеты:** тик телеметрии по-прежнему собирает версии статического списка агента (поведение MVP), а `collect_diagnostics` и `fg_absent` берут список из тени (`WatchedApps`/`desired.watchedApps`).
- Сверх плана: экран статуса опрашивает снимок раз в 3 с только пока виден (реш. 277); `ConnectionMonitor` и `GetAgentStatus`; тест «каждый тип `CommandTypes` известен агенту».

## Что не проверено

- **Ничего не запускалось на эмуляторе** (по плану ручных проверок внутри вехи нет): мастер и статус проверены unit-тестами ViewModel и Robolectric (открытие Lab из мастера, «назад», отсутствие Lab в release); провижининг против живого стенда (`https://10.0.2.2:8443`, CA стенда) — только MockWebServer с собственным CA (успех, чужой CA → `tls_error`, нет CA → запрос не уходит). Всё это — валидация КМ5 (S1).
- `probe_state` от реального Toxiproxy (S7′), пороги на реальных изменениях батареи и тепла, `fg_absent` на реальном usage access, задержка досылки при живой связи — не измерялись (КМ5).
- Release-провижининг с системным доверием не проверялся: CA стенда в release нет (как и для MQTT до MVP-B).
- Время `collect_diagnostics` при многих целях и медленной сети: потолок команды 60 с, пробы идут параллельно, каждая со своим `timeoutMs` — граничный случай не мерился.
- Ревью вехи не проводилось: одно ревью на этап после КМ4 (план).

## Что важно знать КМ4 (симулятор)

- Агент теперь шлёт события `threshold`, `fg_changed`, `fg_absent`, `probe_state` (на каждый переход, включая `UNKNOWN → UP` после старта) — форматы по фикстурам `shared:protocol`; симулятору стоит вести себя так же (`ProbeStateMachine` из `shared:probes`, `ProbeSchedule.forStand()` на стенде).
- `status.role` агент берёт из ответа `/provision` (реш. 210); симулятор — так же.
- Ответы на `run_probe` / `collect_diagnostics` — `succeeded` со строковым `result`: `run_probe` → `target, ok, status?, error?, totalMs`; `collect_diagnostics` → `seq, probes, probesOk, probesFailed, unavailable`; неизвестная цель — `failed`/`unknown_target` (реш. 268).
- Агент считает команду истёкшей, только если `now > expiresAt + 5 мин` (реш. 206) — замер задержки команды в эксперименте от этого не зависит.

## Что важно знать КМ5 (валидация на `rf-api36`)

**Сборка с CA стенда.** Debug-APK берёт CA при сборке из `deploy/certs/out/public/ca.crt` (`generateDebugStandTrust`), поэтому сначала стенд: `cd deploy && ./prepare-stand.sh && docker compose --profile dev up -d --wait`, затем `./gradlew :agent:app:assembleDebug`. Без CA сборка проходит, но мастер ответит «В сборке нет CA стенда» (`ca_missing`), а MQTT — `ca_missing`.

**Эмулятор** — только свой AVD: `emulator -avd rf-api36 -no-window -no-audio -no-boot-anim -port 5600`, затем `adb -s emulator-5600 install -r -t agent/app/build/outputs/apk/debug/app-debug.apk` (`-t` обязателен: debug-APK помечен test-only, без него — `INSTALL_FAILED_TEST_ONLY`; поправлено в КМ5, V-3) или `tools/emulators/run-matrix.sh rf-api36 36`.

**Код регистрации** — curl из `K2.md` («Выпустить код»): `POST https://localhost:8443/api/v1/provisioning/tokens` с JWT admin → `code`. Затем либо мастер (адрес по умолчанию `https://10.0.2.2:8443`, ввести код), либо adb (S1 автоматически):

```bash
adb -s emulator-5600 shell am broadcast -a ru.restofleet.agent.DEV_PROVISION \
  -n ru.restofleet.agent/.DevConfigReceiver --es code "$CODE"            # baseUrl по умолчанию https://10.0.2.2:8443
# через Toxiproxy или другой адрес: --es baseUrl https://10.0.2.2:18443
# ответ: result=-1 data="ok deviceId=d-… role=kitchen"; отказ: result=0 data="token_used" (token_invalid, token_expired, rate_limited, tls_error, ca_missing, no_network, …)
```

Код одноразовый: повтор того же кода — `token_used`. Код виден в командной строке `adb shell` на время вызова (только debug). Старый путь `DEV_CONFIG` (готовая учётка) работает как прежде, но роли в `status` у такой учётки нет.

**После регистрации** агент сам перезапускает MQTT-сессию (смена учётки), экран статуса показывает `подключён`, `connId`, роль, ресторан; `GET /api/v1/devices` — `online`. Для S7′ цель пробы задаётся `PUT /devices/{id}/shadow` (`probes: [{id: "api", type: "http", url: "https://10.0.2.2:18443/health", intervalSec: 5, timeoutMs: 3000, failThreshold: 3}]`); debug-агент проверяет не чаще раза в 5 с, `probe_state: down` — после 3 неудач подряд. Capability Lab (debug) — кнопка внизу экрана статуса.
