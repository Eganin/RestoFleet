## Находка 469 (FR-BR-08, потеря QoS 1 при рестарте брокера)

**Вывод: гипотеза реш. 469 по коду и конфигу не подтверждается и не опровергается.** Ни конфиг брокера, ни код агента не объясняют потерю очереди при штатном рестарте. При этом есть два более простых объяснения, которые надо исключить первыми. Без эксперимента причину не установить.

Что видно в конфиге и коде:
- `deploy/mosquitto/mosquitto.conf`: `persistence true`, `persistence_location /mosquitto/data/`, `autosave_interval 60`, `persistent_client_expiration` не задан (по умолчанию постоянные сессии не истекают). Каталог — именованный том `mosquitto-data` (`deploy/docker-compose.yml:44`). Mosquitto запускается через `exec`, то есть это PID 1, и `docker compose restart` шлёт SIGTERM брокеру. При штатном завершении база пишется на диск целиком, так что `autosave_interval` влияет только на аварийную остановку (SIGKILL, OOM, питание): там теряется до 60 с изменений. Для SIGTERM-рестарта из теста и для `compose restart` он причиной быть не может.
- Агент: `cleanStart = false`, `sessionExpirySec = 86 400` (`agent/data/.../mqtt/MqttSessionConfig.kt:55,65-66`). Те же значения передаются и при первом подключении, и при автопереподключении HiveMQ (`HiveMqLink.kt:83-84`, `:188-189`), подписка — QoS 1 (`:109`). Со стороны агента постоянная сессия настроена правильно.
- `TestBroker.restart()` (`server/data/src/test/.../support/TestBroker.kt:118-129`) шлёт SIGTERM процессу mosquitto, persistence сохраняется. Бэкенд после рестарта получает `session present: true` — значит, восстановление сессий в принципе работает.

Почему гипотезе «Mosquitto не восстанавливает сессии без соединения или клиентов DynSec из `$CONTROL`» рано верить:
1. **Возможный артефакт теста.** Сам тест, показавший потерю, в репозитории не сохранился. Нынешний `BrokerRestartDeliveryTest.kt:37` после рестарта подключает устройство с `cleanStart = true`. По MQTT 5 (3.1.2.4, 3.2.2.1.1) при Clean Start = 1 брокер обязан отбросить сессию и ответить `session present = 0`. Если и в первоначальном эксперименте было такое подключение, наблюдение «`session present: false`, команды нет и после повторной подписки» полностью им объясняется, и Mosquitto тут ни при чём.
2. **Message Expiry у команды.** Команда публикуется с `messageExpiryInterval` (`server/data/.../mqtt/HiveMqPublisher.kt:56`), а retained `desired`, который переживает рестарт, — без него. Возможно, пересчёт срока при загрузке из persistence отбрасывает сообщения со сроком. По коду это не проверить.

Эксперимент для ПМ12 (тот же `TestBroker`, по одному прогону на ячейку): подключение устройства после рестарта с `cleanStart` `false`/`true` × команда с `messageExpiryInterval` и без него × устройство, созданное через `$CONTROL` и через `mosquitto_ctrl`. В каждой ячейке фиксировать `session present` и доставку. Отдельно, на стенде: `docker compose restart mosquitto` с офлайн-агентом (как и запланировано в реш. 469). Только по итогам эксперимента писать причину в журнал и выбирать исправление (повтор `sent`-команд при `online`).

## Проверено и признано корректным

Семейство и потолок наследуются, срок — `min(now + 24 ч, потолок)`. `logout` отзывает семейство и всегда отвечает 204. Повтор токена после выхода даёт 401 без `revokeAll` (у семейства нет живого преемника). Длина токена ограничена 256 символами, у самого токена 32 случайных байта. `noStore` выставлен на ответах `login` и `refresh`.
- **JWT.** HS256, issuer и audience проверяются, `exp` — верификатором auth0, роль `admin` — в `validate`. Access живёт 15 мин.
- **WebSocket (реш. 418, 419).** Маршрут под `authenticate(ADMIN)`, токен берётся только из заголовка (JWT-провайдер query не читает). Закрытия работают по описанию: 4401 по `exp`, 1008 на пятое соединение, шестую подписку или нераспознанный фрейм, 1013 при переполнении очереди 256. `writer` и `expiry` отменяются в `finally`, `unregister` тоже в `finally`. Шина — `tryEmit`: при потерях счётчик и `resync`. В nginx лог без query (`rf_noquery`), upgrade проксируется.
- **Авторизация REST.** Все новые операции — `alerts`, `summary`, `incidents`, история команд, `restaurants`, `provisioning/tokens`, `ws` — под `authenticate(ADMIN)`. Без JWT по замыслу остаются только `login` (rate limit), `refresh`, `logout`, `provision` (rate limit) и `/poll/*` (Basic с лимитом неудач).
- **Инъекции.** `q` в `/devices` экранируется: `LikePattern.ofLiteral` и escape-символ `\`. Остальные фильтры — перечисления, которые валидируются (иначе 400), длины ограничены, всё параметризовано через Exposed.
- **Логи.** `CallLogging` пишет путь без query, заголовков и тел. Нераспознанное сообщение логируется без payload. В консоли журнал Ktor только в debug, уровень `HEADERS`, `Authorization` вырезается. `toString` у токенов и учёток маскирует секреты. Коды провижининга в логи не пишутся.
- **bcrypt по фиктивному хэшу (реш. 468).** Есть в `Login` и в `AuthenticateDevice`: неизвестное, отозванное и выведенное устройство идут через bcrypt. Ранний выход есть только для синтаксически неверного `deviceId`, а формат не секрет.
- **Хранение в консоли (реш. 420, 423).** Ключ Keystore AES-256-GCM, неэкспортируемый. Конверт версионирован, лежит в DataStore, access хранится только в памяти. `allowBackup=false`, `dataExtractionRules` и `fullBackupContent` исключают все домены. CA стенда подключается только в debug-манифесте через `debug-overrides`, есть задача `verifyReleaseNoDebugSurface` (не запускалась — см. `P-console.md`). Адрес сервера принимается только `https` и без userinfo.
- **`RuleEngine` R-01…R-06 (реш. 413, 415).** Тревога открывается по входу в условие и закрывается автоматически по выходу. Повторный вход поглощается. После ручного закрытия новая тревога открывается только при новом входе. R-02 учитывает `charging`, у R-06 гистерезис 500/600. Дедупликация двойная: проверка `existing == null` и частичный уникальный индекс с `insertIgnore`.
- **Агрегатор и классификатор (разд. 4.2, реш. 409–412, 416).** P ≥ 50 % считается от онлайн-устройств с данными, при живом `ref`. M = max(3, ⌈0,25·N⌉). Долю офлайн учитывают только при ≥ 2 устройствах. Офлайн-устройства не входят в знаменатель, неучитываемые устройства (24 ч, выведенные) отбрасываются. Рестораны с R-07 исключаются из A. Закрытие — после двух тиков подряд, `superseded` срабатывает при смене типа. Подавление соответствует реш. 416 и пересчитывается целиком.
- **Транзакции.** `AlertProcessor` работает в транзакции `IngestBatch` и `HandleStatus`, ack брокеру уходит после commit. Шина публикует после commit во всех use cases. Тик идёт под `pg_try_advisory_xact_lock`. Повторная доставка пачки идемпотентна (кроме дубля событий — реш. 207).
- **Перехватчик refresh консоли (реш. 474).** Параллельные 401 дают один refresh: Mutex и сравнение с токеном, который отказал. Новая пара сохраняется до повтора запроса. Повтор один, refresh идёт через клиент без перехватчика, поэтому цикла нет. Refresh после выхода получает `SessionEnded`, `Rejected` ведёт на экран входа.
- **Переподключение WS (кроме RV-2, RV-3, RV-13).** Backoff 1…30 с с jitter и сбросом по `hello`. 4401 → refresh и сразу заново; 1008 → пауза 60 с; `SessionLost` при отказе refresh. Подписки переотправляются, `Connected` вызывает перечитывание.
- **Слои и DI консоли.** Domain-модули фич без фреймворков, `-ui` зависит только от `-domain` и `core`. Koin используется только в `di` и `component`, внедрение через конструктор. У `BaseMviViewModel` scope с `SupervisorJob` и обработчиком исключений.
- **Агент.** V-4 (реш. 464): счётчик возвратов сети; прерываются ретрайная пауза и ожидание автопереподключения, пауза `auth_failed` не прерывается. R-12: учётка записывается под `NonCancellable`, клиент провижининга работает без повторов и редиректов. R-14: событие сначала в outbox, состояние фиксируется потом (`preview`, `copy`, `checkpoint`/`restore`). R-15: интервал держится через `lastRun` по монотонным часам. `UNKNOWN → UP` после перезапуска агента снимает устаревший `down` на сервере. R-13 (кнопка на экране статуса) подробно не разбирался.

Не разбирались: симулятор и `tools/incidents` (точность), `docs/practice`, `app-desktop` (кроме лимита соединений), экраны консоли на соответствие макету.
