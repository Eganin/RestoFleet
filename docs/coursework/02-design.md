# 2 Проектирование системы

## 2.1 Требования к системе

Требования к системе сформулированы в техническом задании, структура которого адаптирована по ГОСТ 34.602-2020 [30]. Каждому требованию присвоен идентификатор вида FR-AG-nn (агент), FR-BR-nn (брокер), FR-BE-nn (серверная часть), FR-SM-nn (симулятор) и метка этапа; в курсовую работу включены требования этапа «К», получившие в проверке осуществимости (подраздел 1.5.3) оценку «работает» или «работает с ограничением».

**Android-агент** (обычный режим) должен работать как служба переднего плана с автозапуском, сторожем, мастером разрешений и экраном статуса (FR-AG-01…05); регистрироваться по одноразовому коду и хранить учётные данные с Android Keystore (FR-AG-10, 12); передавать телеметрию о питании, тепловом состоянии, сети, памяти, приложениях (FR-AG-20…23, 25…27); выполнять HTTP(S)-проверки доступности целей с классификацией ошибок, замером этапов и порогом K неудач, в том числе без связи с платформой (FR-AG-30…35); немедленно сообщать о событиях (FR-AG-40…44); применять и подтверждать тень (FR-AG-50, 51, 53); исполнять команды `ping`, `show_message`, `collect_diagnostics`, `launch_app`, `run_probe` идемпотентно и с учётом срока жизни (FR-AG-60…64, 70…72); буферизовать сообщения до 24 ч и переподключаться с задержкой, зависящей от причины разрыва (FR-AG-75, 76, 78…80).

**MQTT-брокер** должен поддерживать MQTT 5.0 и 3.1.1 поверх TLS, аутентифицировать устройства по логину и паролю, ограничивать каждое устройство его собственными топиками, позволять создавать и блокировать учётные записи без перезапуска, хранить постоянные сессии и данные на диске (FR-BR-01…03, 07, 08, базовый FR-BR-04).

**Серверная часть** должна вести реестр ресторанов и устройств, выпускать одноразовые коды регистрации и обменивать их на учётные данные, выводить устройства из эксплуатации (FR-BE-01, 02, 04); принимать телеметрию, результаты проверок, события и статусы через разделяемую подписку с подтверждением брокеру после записи в базу данных и с дедупликацией результатов команд (FR-BE-10…12, 14); хранить тени и публиковать желаемое состояние (FR-BE-20, 21); отправлять команды и вести их статусы (FR-BE-40, 41); предоставлять REST API с описанием OpenAPI, аутентификацию по JWT, конечные точки REST-polling для эксперимента и `/health` (FR-BE-50, 52, 54, 56).

**Симулятор** должен запускать в одном процессе множество виртуальных устройств с поведением, идентичным агенту, профилями кухни, зала и сборки, режимом REST-polling, сценариями в YAML, выводом результатов в CSV и регистрацией через тот же провижининг (FR-SM-01…03, 06, 07, базовый FR-SM-08).

В курсовую работу не входят правила и тревоги, корреляция инцидентов, консоль оператора и режим Device Owner — они реализуются на этапах практики и выпускной работы. Демонстрация выполняется через Swagger UI, MQTT-клиент MQTT Explorer и экраны агента. Нефункциональные требования этапа приведены в таблице 2.1.

| Сопровождаемость | Kotlin, Clean Architecture с проверкой правила зависимостей, покрытие тестами: проект ≥ 80 %, domain ≥ 90 %; стенд разворачивается одной командой |

## 2.2 Архитектура системы

### 2.2.1 Состав системы

Система состоит из пяти подсистем (рисунок 2.1): Android-агента, MQTT-брокера Eclipse Mosquitto 2.1, серверной части на Ktor с базой данных PostgreSQL 17, симулятора устройств и консоли оператора (в курсовой работе её заменяет Swagger UI). Все серверные компоненты, а также Toxiproxy для имитации отказов и задержек сети разворачиваются на стенде Docker Compose.

[[FIG: system-overview | Структурная схема системы RestoFleet | Слева блок «Ресторан» с тремя агентами (кухня, зал, сборка). В центре блок «Стенд RestoFleet (Docker Compose)»: Mosquitto 2.1 (TLS 8883, Dynamic Security), Backend (Ktor + Koin), PostgreSQL 17, Toxiproxy, nginx (TLS для REST). Справа внизу «Симулятор устройств», справа вверху «Консоль / Swagger UI». Внешний блок «Бэкенд компании, кухонная станция, эталонная цель». Стрелки: агенты → Mosquitto «MQTT 5 / TLS»; агенты (регистрация) и Консоль / Swagger UI → nginx «HTTPS 8443» → Backend «HTTP 8080, только внутри стенда» (+WebSocket — П); симулятор → Mosquitto «MQTT 5» и → Backend «REST-polling»; Mosquitto → Backend «$share/backend/…»; Backend → Mosquitto «$CONTROL/dynamic-security/v1»; Backend → PostgreSQL; агенты → внешние цели «HTTPS-проверки» (на стенде — Toxiproxy → nginx → /health)]]

Агенты и симулятор подключаются к брокеру по MQTT 5.0 поверх TLS. Серверная часть получает сообщения через разделяемую подписку `$share/backend/…`, что допускает несколько её экземпляров, и управляет учётными записями устройств через топик `$CONTROL/dynamic-security/v1`; консоль работает только через REST API. Серверная часть принимает HTTP только внутри сети стенда, а TLS для REST API и регистрации завершается на обратном прокси nginx. Проверки доступности агент выполняет напрямую к целям; на стенде цель `api` — это `/health` серверной части, доступный через Toxiproxy и nginx, что позволяет имитировать её отказ и деградацию.

### 2.2.2 Clean Architecture

Все части системы построены по принципам Clean Architecture [31]: код разделён на слои domain, data и presentation, а зависимости направлены внутрь — к домену (рисунок 2.2).

[[FIG: clean-layers | Слои Clean Architecture и правило зависимостей | Концентрические окружности: в центре «domain — сущности, use cases, порты (интерфейсы репозиториев, Clock, IdGenerator)»; вокруг «data — репозитории, источники данных, DTO протокола, мапперы» и «presentation — MVI-экраны агента, маршруты Ktor»; внешнее кольцо «composition root — модули Koin, Application, main». Стрелки зависимостей только внутрь. Подписи примеров: agent:domain, agent:data, server:domain, server:data, server:api]]

**Domain** содержит сущности, порты и сценарии использования (use cases) и не зависит от Android SDK, Ktor, Exposed, Room, MQTT-клиента, сериализации и DI-контейнера. **Data** реализует порты: репозитории, источники данных, DTO протокола и мапперы. **Presentation** — экраны агента по шаблону MVI и маршруты Ktor, обращающиеся к домену только через use cases. **Composition root** собирает граф объектов средствами Koin [32] с внедрением через конструктор. Время и генерация идентификаторов вынесены в порты, что делает use cases детерминированно тестируемыми. Правило зависимостей обеспечивается Gradle-модулями и архитектурными тестами Konsist (таблица 2.2).

Таблица 2.2 — Модули системы

| Часть | domain | data | presentation | composition root |
|---|---|---|---|---|
| Общие модули | `shared:kernel` (ошибки, `Outcome`, `Clock`); `shared:shadow` (дельта, версии, проверка параметров); `shared:probes` (автомат up/down, классы ошибок) | `shared:protocol` (DTO, топики, эталонные JSON) | — | — |
| Агент | `agent:domain` | `agent:data` (считывания, проверки OkHttp, MQTT-клиент HiveMQ, outbox на Room, Keystore) | `agent:presentation` (мастер, статус, Capability Lab) | `agent:app` (служба, приёмники, сторож, Koin) |
| Серверная часть | `server:domain` | `server:data` (Exposed, Flyway, приём MQTT, клиент Dynamic Security, bcrypt) | `server:api` (маршруты Ktor [33], OpenAPI, JWT) | `server:app` (`main`, Koin, конфигурация, команды `migrate`, `seed`) |
| Симулятор | `server:simulator` — слои пакетами внутри модуля | | | |

Модуль `shared:protocol` используют агент, серверная часть и симулятор, что исключает расхождение форматов; каждый формат закреплён эталонным JSON-файлом, на котором проверяется сериализация в обе стороны. MQTT-клиент на агенте и сервере — HiveMQ MQTT Client [34].

## 2.3 Протокол взаимодействия

### 2.3.1 Дерево топиков

Топики имеют префикс `rf/v1/`, где `v1` — версия протокола, позволяющая в будущем вводить несовместимые изменения без конфликта с работающими агентами. Каждое устройство имеет собственное поддерево `rf/v1/dev/{deviceId}/` (таблица 2.4, рисунок 2.3).

Таблица 2.4 — Топики протокола

| Топик (после `rf/v1/dev/{deviceId}/`) | Направление | QoS | Retained | Назначение |
|---|---|---|---|---|
| `status` | Устройство → (и завещание от брокера) | 1 | Да | `online` / `offline` |
| `telemetry` | Устройство → | 0 (досылка из буфера — 1) | Нет | Периодическая телеметрия |
| `probe` | Устройство → | 0 (досылка из буфера — 1) | Нет | Результаты проверок доступности |
| `events` | Устройство → | 1 | Нет | События |
| `shadow/reported` | Устройство → | 1 | Нет | Фактическое состояние тени |
| `shadow/desired` | → Устройство | 1 | Да | Желаемое состояние тени |
| `cmd/req` | → Устройство | 1 | Нет | Команды с ограниченным сроком жизни |
| `cmd/res` | Устройство → | 1 | Нет | Результаты команд |

[[FIG: topic-tree | Дерево топиков протокола rf/v1 | Дерево: корень rf → v1 → dev → {deviceId} → листья status, telemetry, probe, events, shadow (→ reported, desired), cmd (→ req, res). Цветом отметить направление: от устройства (status, telemetry, probe, events, shadow/reported, cmd/res) и к устройству (shadow/desired, cmd/req). Пометки «retained» у status и shadow/desired, «LWT» у status. Отдельно пунктиром ветка rf/v1/rest/{restaurantId}/broadcast с пометкой «этап Д»]]

Серверная часть подписывается на `$share/backend/rf/v1/dev/+/{status, telemetry, probe, events, shadow/reported, cmd/res}`. Ответ на команду агент всегда публикует в собственный `cmd/res`. Нечитаемые сообщения, пустой сохраняемый `desired` (очистка) и сообщения в чужой топик подтверждаются брокеру и отбрасываются, чтобы не блокировать сессию повторной доставкой.

### 2.3.2 Форматы сообщений

Сообщения передаются в JSON (UTF-8); поля со значением `null` не передаются, значения по умолчанию пишутся явно. Время — в миллисекундах от начала эпохи Unix. Ниже приведены сокращённые примеры; полный набор форматов закреплён эталонными файлами протокола.

Статус подключения публикуется агентом после подключения; завещание отличается полями `state` и `reason`:

```json
{ "state": "online", "ts": 1793865600000, "connId": "k-7f3a9c",
  "agentVersion": "1.0.0", "mode": "normal", "role": "kitchen", "bootId": "b7f2c1d0",
  "device": { "model": "…", "manufacturer": "…", "osVersion": "16", "apiLevel": 36 } }
{ "state": "offline", "ts": 1793865600000, "connId": "k-7f3a9c", "reason": "lwt" }
```

Телеметрия содержит группы `battery`, `thermal`, `net`, `storage`, `memory`, приложение на экране и версии приложений; результат проверок — массив по целям с полями `ok`, `status`, `error`, `totalMs`, `dnsMs`, `connectMs`, `tlsMs`, `ttfbMs`, где `error` принимает значения `dns_fail`, `timeout`, `conn_refused`, `tls_error`, `http_4xx`, `http_5xx`, `no_network`, `local_network_denied`, `other`.

События различаются полем `type`. Основные из них: `probe_state` — смена состояния цели (`target`, `state` — `up` или `down`, класс последней ошибки `error`, число неудач подряд `failures`); `threshold` — пересечение порога (`metric` — `battery_low`, `temp_high` или `thermal`, `state` — `enter` или `exit`, `value`, `limit`); `fg_changed` — смена приложения на экране (`from`, `to`); `fg_absent` — отслеживаемое приложение `pkg` отсутствует на экране дольше `fgAbsentMin` (`sinceTs`, `limitMin`). Кроме них передаются `net_changed`, `package_changed` и `agent_lifecycle`. Пороги проверяет агент и сообщает только о входе в зону и выходе из неё с гистерезисом 2 % или 2 °C, а не о каждом снимке; для `thermal` порог — уровень `SEVERE`, параметра тени для него нет.

Желаемое состояние тени:

```json
{ "version": 12,
  "telemetry": { "intervalSec": 30 },
  "thresholds": { "batteryLowPct": 20, "tempHighC": 45, "fgAbsentMin": 10 },
  "watchedApps": ["com.android.chrome"],
  "probes": [ { "id": "api", "type": "http", "url": "https://api.company.example/health",
                "intervalSec": 30, "timeoutMs": 5000, "failThreshold": 3 } ] }
```

Для цели может быть задан ожидаемый HTTP-код `expectedStatus`: без него проверка успешна при коде меньше 400, с ним — только при точном совпадении. Фактическое состояние повторяет структуру и добавляет `appliedVersion`, `appliedAt` и `errors`. Версия старее сохранённой игнорируется, равная лишь повторяет `reported`, более новая применяется. Неверный параметр (интервал вне 10…3600 с, пустой или повторный идентификатор цели, некорректное имя пакета) не применяется, а его код возвращается в `errors`. Дельту вычисляет серверная часть; она пуста, когда параметры применены.

Команда и ответы на неё:

```json
{ "cmdId": "c-01J9Z3", "type": "show_message",
  "params": { "text": "Перезагрузите роутер", "level": "warning" }, "expiresAt": 1793866100000 }
{ "cmdId": "c-01J9Z3", "status": "received", "ts": 1793865800000 }
{ "cmdId": "c-01J9Z3", "status": "succeeded", "ts": 1793865801000, "result": {} }
```

Команда публикуется со свойствами MQTT 5.0 `Response Topic = rf/v1/dev/{id}/cmd/res`, `Correlation Data = cmdId` и `Message Expiry Interval`, равным оставшемуся сроку жизни команды (по умолчанию 300 с, не более 24 ч). Ответ `received` публикуется сразу при получении, затем — один итоговый статус: `succeeded` (с объектом `result` со строковыми значениями), `failed` или `unsupported` с полем `reason` (например, `expired`, `timeout`, `invalid_params:…`, `requires_device_owner`).

### 2.3.3 Параметры сессии

Параметры MQTT-сессии агента выбраны исходя из требований к обнаружению пропажи устройства и доставке команд:

- Keep Alive — 30 с; завещание публикуется в `status` с флагом retained и QoS 1; на каждую попытку подключения генерируется новый `connId`, общий для `online` и завещания этого подключения;
- Clean Start = 0, Session Expiry Interval — 24 ч: команды для отключённого устройства ждут его в брокере;
- идентификатор клиента равен `deviceId` и привязан к учётной записи; повторное подключение с тем же идентификатором вытесняет прежнюю сессию (код 0x8E);
- подписки QoS 1 на `shadow/desired` и `cmd/req` оформляются при каждом подключении; входящие сообщения агент подтверждает брокеру после их обработки;
- повторное подключение выполняется с экспоненциальной задержкой со случайным разбросом 1…120 с; при отказе в аутентификации — через 15, 30, затем каждые 60 мин; при вытеснении сессии — через 5 мин со случайной добавкой до 1 мин; это исключает лавину переподключений после сбоя.

### 2.3.4 Правки протокола

Анализ исходной версии протокола при проектировании и проверке осуществимости выявил десять проблем, устранённых правками P1–P10 (таблица 2.5).

Таблица 2.5 — Правки протокола P1–P10

| № | Проблема | Правка |
|---|---|---|
| P1 | Статус команды «доставлена» средствами MQTT не узнать | Агент сразу публикует `cmd/res` со статусом `received`, затем итоговый |
| P2 | Брокер не сообщает об истечении срока команды | Поле `expiresAt` в команде и Message Expiry брокера; сервер переводит команду в `expired` по таймеру, поздний итоговый ответ имеет приоритет; агент не исполняет истёкшую команду |
| P3 | Завещание старой сессии может прийти после `online` новой | `connId` в `online` и в завещании; завещание с чужим `connId` игнорируется |
| P4 | Разделяемая подписка не получает сохраняемых сообщений | Источник истины статуса устройства — база данных |
| P5 | ACL по шаблону «всё под своим именем» позволяет устройству писать себе `desired` и `cmd/req` | Роль `device` с ACL по направлениям (таблица 2.7) |
| P6 | Идентификатор клиента не привязан к учётной записи | Учётная запись Dynamic Security с `clientid = deviceId` |
| P7 | Порог правила «устройство вне сети» не согласован с требованием ко времени обнаружения | Keep Alive 30 с, событие по завещанию без задержки ⇒ ≈ 50 с |
| P8 | Брокер не сохраняет данные на диск | `persistence true` и том Docker; очистка сохраняемых сообщений при выводе устройства |
| P9 | Аутентификация в режиме REST-polling не описана | HTTP Basic с учётными данными устройства, на сервере — bcrypt-хэш |
| P10 | Без ручного подтверждения доставка QoS 1 без потерь не гарантируется | Постоянный идентификатор клиента, Clean Start = 0, подтверждение после записи пакета в БД |

Правка P8 реализуется параметрами `persistence` и `persistence_location` конфигурации Mosquitto [35], благодаря которым сохраняемые сообщения и постоянные сессии не теряются при перезапуске брокера.

### 2.3.5 Гарантии доставки

Протокол обеспечивает доставку «по меньшей мере один раз» (at-least-once) для всех сообщений, кроме текущей телеметрии и результатов проверок, которые при наличии связи передаются с QoS 0 и могут теряться — их ценность быстро устаревает.

Агент использует персистентный буфер исходящих сообщений (outbox) на Room — аналог шаблона «транзакционный исходящий ящик» [36]. События, `reported` и результаты команд записываются в буфер и удаляются только после подтверждения брокера (PUBACK); без связи туда же попадают телеметрия и проверки. При непустом буфере новое сообщение ставится в очередь, чтобы не обогнать более раннее. Досылка идёт пачками по 50 не быстрее 20 сообщений в секунду, результаты команд — вне очереди телеметрии. Окончательный отказ брокера в PUBACK (например, 0x87) удаляет запись, временный — останавливает досылку до следующей попытки.

Команды исполняются «не более одного раза»: агент публикует `received`, записывает `cmdId` в персистентный журнал последних 200 команд, исполняет команду и публикует итог; повторная доставка той же команды по журналу не исполняется. Истёкшей считается команда, у которой текущее время устройства превышает `expiresAt` более чем на 5 мин — допуск на расхождение часов; основная защита — Message Expiry брокера, не зависящий от часов устройства. Последовательность обработки команды показана на рисунке 2.4.

[[FIG: cmd-sequence | Последовательность отправки и исполнения команды | Диаграмма последовательности с участниками: Оператор (Swagger UI), Backend, PostgreSQL, Mosquitto, Агент. Шаги: 1) POST /devices/{id}/commands; 2) Backend сохраняет команду (queued) и публикует cmd/req QoS 1 с Response Topic, Correlation Data, Message Expiry 300; 3) если агент офлайн — брокер хранит в сессии; 4) агент получает, публикует cmd/res received через outbox; 5) Backend → delivered; 6) агент записывает cmdId в журнал, исполняет, публикует succeeded/failed/unsupported; 7) Backend → итоговый статус, дедупликация по (cmdId, status); 8) агент подтверждает cmd/req брокеру после обработки; альтернатива: таймер Backend → expired, если итога нет к expiresAt]]

Повторы обрабатываются идемпотентно: результаты команд дедуплицируются по паре `(cmdId, status)`, телеметрия — уникальностью пары «устройство — время измерения»; у событий идентификатора нет, и одиночный дубль при обрыве досылки признан допустимым. Статусы команды на сервере: `queued` → `delivered` (по `received`) → `succeeded` / `failed` / `unsupported` / `expired`.

## 2.5 Безопасность

Меры безопасности направлены против перехвата и подмены трафика, подключения постороннего устройства, действий скомпрометированного устройства от имени других и компрометации учётных данных пользователей.

**Защита каналов.** Все каналы защищены TLS версии 1.2 и выше [37; 38]: MQTT — на порту 8883, REST API и регистрация — через обратный прокси nginx стенда, за которым серверная часть принимает HTTP только внутри сети стенда. Сертификаты выпускаются собственным удостоверяющим центром стенда с альтернативными именами для всех адресов брокера и сервера; MQTT-клиент агента доверяет только этому центру (закрепление сертификата) и не подключается при его отсутствии. Регистрация в отладочной сборке использует то же закрепление, в выпускной — системное хранилище сертификатов.

**Аутентификация и авторизация устройств.** Брокер не принимает анонимных подключений; учётными записями управляет расширение Dynamic Security [39], в котором клиенты, группы и роли с правилами ACL изменяются без перезапуска брокера командами в управляющий топик. Каждое устройство получает учётную запись с логином и идентификатором клиента, равными `deviceId`, и паролем из 32 случайных байт, который передаётся устройству один раз. Права устройства задаёт роль `device` (таблица 2.7); по умолчанию публикация и подписка запрещены.

Таблица 2.7 — Права роли `device` в брокере

| Операция | Разрешённые топики (только собственные, `rf/v1/dev/{deviceId}/…`) |
|---|---|
| Публикация | `status`, `telemetry`, `probe`, `events`, `shadow/reported`, `cmd/res` |
| Подписка | `shadow/desired`, `cmd/req` |
| Всё остальное | Запрещено, в том числе публикация в собственные `shadow/desired` и `cmd/req` и любой доступ к топикам других устройств |

Проверка на стенде подтвердила, что публикация устройства в чужой топик и в собственный `cmd/req` отклоняется кодом 0x87, а отключение учётной записи разрывает текущую сессию устройства за 16 мс.

**Провижининг.** Администратор выпускает для ресторана и роли одноразовый код регистрации со сроком действия 24 ч; код содержит 128 случайных бит и хранится в базе только в виде хэша SHA-256. Агент обменивает код на учётные данные запросом `POST /api/v1/provision`. В одной транзакции сервер погашает код (только не использованный и не просроченный), создаёт устройство с ролью и рестораном из кода, сохраняет bcrypt-хэш пароля и тень с желаемым состоянием по умолчанию и последним шагом создаёт учётную запись в брокере с ролью `device`; отказ брокера откатывает транзакцию, и код остаётся действительным. После фиксации сервер публикует сохраняемый `desired` версии 1 и возвращает `deviceId`, пароль, ресторан, роль и адрес брокера (рисунок 2.6). Неизвестный код отклоняется с кодом HTTP 401 (`token_invalid`), погашенный — 409 (`token_used`), просроченный — 410 (`token_expired`), превышение частоты — 429 (`rate_limited`), недоступность брокера — 503 (`broker_unavailable`) с возможностью повтора. Роль задаётся при выпуске кода и не выбирается на устройстве, поэтому код, выданный для устройства зала, не позволяет зарегистрировать устройство кухни. Вывод устройства из эксплуатации отключает учётную запись в брокере, отзывает учётные данные и удаляет сохраняемые сообщения устройства.

[[FIG: provisioning-sequence | Последовательность провижининга устройства | Диаграмма последовательности с участниками Администратор (Swagger UI), nginx, Backend, PostgreSQL, Mosquitto, Агент. 1) Администратор → nginx → Backend: POST /api/v1/provisioning/tokens {restaurantId, role, name} (JWT) → Backend сохраняет SHA-256 кода, возвращает код (TTL 24 ч). 2) Администратор передаёт код технику. 3) Агент (мастер) → nginx (HTTPS 8443) → Backend: POST /api/v1/provision {code, deviceInfo, agentVersion}. 4) Backend, одна транзакция: погашение кода UPDATE … RETURNING (не использован, не истёк); создание device (provisioned, роль и ресторан из кода); генерация пароля (32 байта) и сохранение bcrypt-хэша; тень desired v1; Backend → Mosquitto $CONTROL/dynamic-security/v1: createClient (username = clientid = deviceId, роль device той же командой); commit. **Пользователи и API.** Пароли хранятся в виде хэшей bcrypt [40] — адаптивной функции с настраиваемой стоимостью. Доступ к API — по маркеру JWT [41], подписанному алгоритмом HS256, сроком 15 мин и маркеру обновления сроком 7 сут, который хранится в виде хэша SHA-256 и заменяется при каждом использовании; повторное предъявление уже заменённого маркера считается признаком кражи и отзывает все маркеры пользователя. Частота запросов входа (10 в минуту) и регистрации (60 в минуту) с одного адреса ограничена. В режиме REST-polling устройство аутентифицируется по HTTP Basic; чтобы эксперимент измерял протокол, а не стоимость bcrypt, успешные проверки кэшируются на 5 мин.

**Агент.** Учётные данные шифруются по AES-256/GCM ключом из Android Keystore и исключены из резервного копирования. Привилегированные действия Device Owner по вводу пользователя есть только в отладочной сборке; единственный доверенный источник `desired` и команд — сервер.

Поскольку консоли оператора на этом этапе нет, действия выполняются через Swagger UI, а поток сообщений наблюдается в MQTT Explorer; штрих в обозначении сценария указывает на сокращённый вариант без тревог, которые появятся на этапе практики.

## 2.7 Выводы по главе

1. Требования этапа сформулированы по подсистемам (FR-AG, FR-BR, FR-BE, FR-SM); нефункциональные требования задают масштаб 1 000 устройств, обнаружение пропажи устройства за ≈ 50 с, доставку команды онлайн-устройству за 2 с (p95) и отсутствие потерь событий за 24 ч без связи.
2. Система состоит из агента, брокера Mosquitto 2.1 с Dynamic Security, серверной части на Ktor с PostgreSQL и симулятора; все части построены по Clean Architecture и используют общий модуль протокола.
3. Протокол поверх MQTT 5.0 задаёт дерево топиков с версией, форматы сообщений, параметры сессии и правки P1–P10, восполняющие отсутствующие в MQTT статусы доставки и истечения команд, устраняющие гонку завещаний и ограничивающие права устройств.
4. Доставка «по меньшей мере один раз» обеспечивается буфером агента, подтверждением входящих сообщений после обработки, подтверждением брокеру после записи в БД и идемпотентной обработкой повторов; команды исполняются не более одного раза.
5. Безопасность обеспечивается TLS с собственным удостоверяющим центром, учётными записями устройств с ACL по направлениям, одноразовыми кодами регистрации, bcrypt и JWT, Android Keystore; сценарии S1, S2′, S4, S5 и S7′ задают критерии приёмки реализации.
