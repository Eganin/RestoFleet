# 4 Экспериментальная часть

## 4.1 Цель и метрики эксперимента

Цель эксперимента — количественно обосновать выбор MQTT, сравнив его с периодическим опросом сервера по HTTP (REST-polling, подраздел 1.2.2). Оба режима используют одни классы сообщений (подраздел 3.1), одну серверную часть и одну базу данных, поэтому различия определяются транспортом, а не форматом данных. Конфигурации заданы техническим заданием: N = 100, 1 000 и 5 000 устройств, интервал телеметрии 30 с, интервал опроса команд P = 5, 15 и 30 с; эксперимент должен быть проведён на N ≥ 1 000. Метрики приведены в таблице 4.1.

Таблица 4.1 — Метрики эксперимента

| Метрика | Определение | Источник данных |
|---|---|---|
| Трафик на устройство | Байты, принятые и переданные устройствами за окно замера, в пересчёте на одно устройство и сутки | Счётчики байтов сетевого интерфейса устройств в контейнере симулятора [52] |
| Нагрузка на сервер | Загрузка CPU и потребление ОЗУ контейнеров `backend`, `mosquitto`, `postgres`; поток сообщений или запросов в секунду | `docker stats` [53] раз в 5 с; счётчики симулятора |
| Задержка доставки команды | Время от отправки команды через REST API до её получения устройством; медиана (p50) и 95-й процентиль (p95) | Монотонные часы процесса симулятора |
| Время обнаружения пропажи | Время от прекращения передачи данных устройством до статуса `offline` в реестре | Опрос `GET /devices/{id}` раз в 1 с |
| Поведение при деградации сети | Задержка и доля доставленных команд при задержке 300 мс и потере 5 % пакетов | Те же метрики в прогонах с деградацией |

Часть величин следует из параметров. Команда в режиме REST ждёт очередного опроса со случайной фазой, поэтому её задержка распределена приблизительно равномерно от 0 до P: медиана — около P/2, p95 — около 0,95 P, и требование p95 ≤ 2 с (таблица 2.1) в режиме REST недостижимо по построению. Пропажу REST-устройства определяет порог 3P (подраздел 3.4.4), MQTT-устройства — Keep Alive: брокер закрывает соединение, если в течение 1,5 × Keep Alive от клиента нет пакетов [2], то есть через 45 с. Трафик и нагрузка на сервер определяются измерением.

## 4.2 Методика и стенд

### 4.2.1 Стенд

Эксперимент выполняется на стенде Docker Compose (подраздел 3.6) на одной машине: Apple M1 Pro (10 ядер, 16 ГБ ОЗУ), Docker Desktop 29.2.0, виртуальная машина Docker с 10 CPU и 7,65 ГиБ памяти. Контейнеры `backend`, `mosquitto` и `postgres` работают без ограничений ресурсов, симулятор с измерителем — в контейнере, ограниченном 2 CPU и 3 ГБ памяти, чтобы не отнимать ресурсы у сервера. Все 16 прогонов выполнены последовательно 11–12 ноября 2026 г. (с 20:56 до 00:18 UTC) с паузой 30 с; других ресурсоёмких задач на машине не выполнялось, фоновые процессы операционной системы не останавливались. MQTT-устройства подключаются к брокеру по TLS, REST-устройства — к серверной части по HTTP внутри сети стенда, минуя nginx: шлюз в конфигурации стенда открывает к серверной части новое соединение на каждый запрос, и эксперимент измерял бы его ограничения, а не протокол. Измеритель обращается к REST API по отдельной сети Docker. Все 5 000 устройств зарегистрированы заранее, прогон на N устройств берёт первые N учётных записей, а порог присутствия 3P задаётся серверной части через окружение перед прогоном.

### 4.2.3 Длительность окна замера

Окно замера 600 с равно двум срокам жизни кэша проверок HTTP Basic (5 мин, подраздел 3.4.4); после массового подключения моменты истечения кэша синхронны. Окно короче срока жизни кэша либо не содержит повторных проверок bcrypt и занижает нагрузку REST, либо захватывает одиночный всплеск и завышает её, а окно в два срока при любом моменте первой аутентификации включает повторные проверки каждого устройства. Для единообразия то же окно используется в режиме MQTT. Первая серия из 16 прогонов выполнялась с окном 240 с, короче срока жизни кэша, и задержка первой команды в ней включала вход измерителя; её результаты не используются: методика исправлена, прогоны повторены, ниже приведены результаты второй серии.

### 4.2.4 Деградация сети

Задержка задаётся токсиком `latency` Toxiproxy [48] величиной 300 мс на направлении от сервера к клиенту прокси `mqtt` и `rest`, через которые в этих прогонах подключаются устройства; время кругового обхода увеличивается на 300 мс. Потери задаются дисциплиной очереди `netem` ядра Linux [54] с параметром `loss 5%` на интерфейсе контейнера симулятора и действуют только на исходящий трафик устройств: для входящего направления нужен интерфейс `ifb`, которого нет в ядре виртуальной машины Docker Desktop. Поэтому теряются телеметрия, итоги команд и подтверждения TCP устройства, а команды от сервера потерям не подвержены.

### 4.2.5 Расчёт метрик

Трафик на устройство в сутки:

*V* = 86 400 · (*R* + *S*) / (*N*₀ · *T*),

где *R*, *S* — приращения счётчиков принятых и переданных байтов интерфейса за окно; *N*₀ — число устройств, подключённых к началу окна; *T* — длительность окна, с. Счётчики учитывают IP-пакеты целиком [52]: заголовки TCP/IP, записи TLS, пакеты Keep Alive и подтверждения TCP; для сверки фиксируются объём полезной нагрузки и трафик контейнера по `docker stats`.

Задержка команды — разность моментов получения команды устройством и отправки запроса `POST /devices/{id}/commands` по монотонным часам одного процесса; процентили вычисляются методом ближайшего ранга (элемент с номером ⌈p · n / 100⌉ упорядоченной выборки).

Загрузка CPU сервера в процентах одного ядра суммируется по `backend`, `mosquitto` и `postgres` по замерам `docker stats` раз в 5 с; за окно вычисляются среднее, медиана и пик суммы. ОЗУ — среднее по замерам окна, поток — сообщения MQTT в обоих направлениях или успешные HTTP-запросы в секунду.

Время обнаружения пропажи — интервал от момента, когда устройство перестаёт передавать данные, до первого ответа `GET /devices/{id}` со статусом `offline`; по десяти устройствам вычисляются медиана, минимум и максимум.

Загрузка CPU сервера в режиме MQTT растёт медленно: с 4,4 до 15,2 % ядра при росте N с 100 до 5 000 (в 3,4 раза при росте парка в 50 раз). Главная особенность нагрузки REST связана не с частотой опроса, а с аутентификацией. REST-устройство проходит полную проверку пароля bcrypt при первом запросе и затем раз в срок жизни кэша проверок HTTP Basic (5 мин), тогда как у MQTT пароль проверяется только при подключении, до окна. Поскольку все устройства подключаются за время разгона, сроки кэша истекают почти одновременно, и проверки идут синхронными всплесками высотой до 920–940 % ядра и длительностью около минуты — в разгоне и через ≈ 300 и ≈ 600 с после старта (рисунок 4.4). Окно в два срока жизни кэша содержит одинаковое число повторных проверок при любой фазе, поэтому среднее за окно — стационарная оценка, включающая проверки паролей в той же доле, что и в сутках работы, медиана характеризует фоновую нагрузку между проверками, а пик — высоту всплеска.

[[FIG: timeline-5000 | Загрузка CPU контейнеров сервера во времени при N = 5 000 | График analyze.py (docs/experiments/img/timeline-5000.png): две панели — MQTT и REST с опросом 5 с; линии backend, mosquitto, postgres; ось X — секунды от старта прогона, окно замера выделено серым]]

Вклад проверок паролей, оцениваемый разностью среднего и медианы, составляет 123–136 % ядра при N = 5 000 и 21–25 % при N = 1 000 и от интервала опроса почти не зависит. Поэтому при больших N среднюю загрузку REST определяют повторные проверки bcrypt, а не частота опроса: при N = 5 000 опрос раз в 30 с (187,6 %) лишь немного дешевле опроса раз в 15 с (198,9 %) и составляет 71 % от опроса раз в 5 с (264,8 %). Вклад самого опроса виден по медиане: при N = 5 000 она равна 52,1, 64,5 и 141,6 % ядра при P = 30, 15 и 5 с против 14,4 % у MQTT, то есть в 3,6–9,8 раза больше; при N = 1 000 — в 3,0–4,9 раза. Следовательно, сравнение по средней загрузке относится к REST-polling с выбранной схемой аутентификации — HTTP Basic с проверкой bcrypt и кэшем на 5 мин. При аутентификации по маркерам или более длительном сроке кэша доля проверок паролей уменьшилась бы, и средняя загрузка REST приблизилась бы к фоновой, которая также выше MQTT и растёт с частотой опроса; на реальном парке с подключениями, распределёнными во времени, пик был бы ниже при том же среднем.

Малый разброс внутри прогона объясняется тем, что Mosquitto проверяет Keep Alive пачками: по журналу брокера в одну секунду отключены 10, 9 и 7 из 10 пропавших устройств при N = 100, 1 000 и 5 000, хотя последний пакет каждое из них отправило в своё время. Поэтому время обнаружения определяется фазой такой проверки, а максимум 46,3 с при N = 5 000 превышает 45 с на 1,3 с, что сопоставимо с шагом опроса статуса (1 с) и дискретностью пачечной проверки. У REST время составляет 2,4–2,9 P: порог 3P отсчитывается от последнего опроса, сделанного до пропажи, и проверяется раз в 5 с. Требование ≈ 50 с выполняется в режиме REST только при P ≤ 15 с, а обнаружение быстрее MQTT (13–15 с) достигается при P = 5 с ценой наибольших трафика и нагрузки на сервер.

## 4.7 Ограничения и угрозы достоверности

Результаты эксперимента интерпретируются с учётом следующих ограничений:

1. **Одна машина.** Сервер и симулятор делят ресурсы одной виртуальной машины, сеть между ними — мост Docker без реальной задержки; сравнимы соотношения между режимами, а не абсолютные значения загрузки CPU.
2. **Схема аутентификации REST.** Средняя загрузка CPU REST при N ≥ 1 000 определяется повторными проверками bcrypt раз в срок жизни кэша HTTP Basic (подраздел 4.5); при маркерах доступа или более длительном сроке кэша картина иная, а вклад опроса оценивается по медиане. Одновременное подключение парка завышает пик, но не среднее.
3. **REST без TLS.** Шифрование увеличило бы трафик и нагрузку только у REST, поэтому по этому фактору сравнение консервативно в пользу REST.
4. **Заголовки ограничения частоты.** Ответы на опрос содержат заголовки `X-RateLimit-*` (81 байт), увеличивающие трафик REST на 10–13 %; это свойство реализации серверной части, а не протокола HTTP.
5. **Экстраполяция на сутки.** Суточный трафик получен линейной экстраполяцией окна 600 с; переподключения, истечение сессий и рост базы данных не измерялись. Команды измерителя входят в трафик устройств, поэтому трафик сравним между режимами при одном N.
6. **Потери только на исходящем трафике.** Влияние потерь на задержку доставки команд занижено; проверка в обоих направлениях требует хоста Linux с интерфейсом `ifb` или реальной сети.
7. **REST доставляет «не более одного раза».** Потеря ответа на опрос означает потерю команды, тогда как MQTT доставляет «по меньшей мере один раз» (подраздел 2.3.5), поэтому равная доля доставленных команд не означает равной надёжности.
8. **Объём выборки.** Окно 600 с покрывает малую часть суточного цикла профилей; каждая конфигурация выполнена одним прогоном, выборка времени обнаружения — 10 устройств.
9. **Нет реальных устройств.** Виртуальные устройства не воспроизводят режим Doze, задержки радиомодуля и повторные передачи в сетях Wi-Fi и сотовой связи; замер на реальных устройствах предусмотрен на следующем этапе.

## 4.8 Выводы по главе

1. Трафик MQTT составил 2,55–3,61 МБ в сутки на устройство; REST-polling передаёт в 1,6–2,0 раза больше при опросе раз в 30 с и в 4,2–5,7 раза больше при опросе раз в 5 с за счёт накладных расходов HTTP на каждый опрос (REST измерен без TLS, но с заголовками ограничения частоты).
2. Задержка доставки команды MQTT — 10,9–12,3 мс по медиане и не более 16,3 мс по p95, требование p95 ≤ 2 с выполнено с большим запасом. У REST задержка равна примерно половине интервала опроса (p95 — 0,95 P), и требование недостижимо; при N = 5 000 и P = 5 с всплески проверок паролей задержали 13 из 600 команд сверх интервала.
3. Нагрузка на сервер в режиме MQTT выросла с 4,4 до 15,2 % ядра при росте парка с 100 до 5 000 устройств; у REST средняя загрузка выше в 5–7 раз при N = 1 000 и в 12–17 раз при N = 5 000, причём при больших N её определяют повторные проверки bcrypt раз в срок жизни кэша HTTP Basic, а не частота опроса; по медиане, отражающей вклад опроса, превышение при N = 5 000 составляет 3,6–9,8 раза. Вывод относится к REST с выбранной схемой аутентификации.
4. Пропажа устройства обнаруживается по MQTT за 41–46 с при любом N, требование ≈ 50 с выполнено; у REST время равно 2,4–2,9 интервала опроса, и требование выполняется только при P ≤ 15 с.
5. При задержке 300 мс и потерях 5 % на исходящем трафике устройств оба режима доставили все команды без обрывов соединений.
6. В исследованной конфигурации MQTT превосходит REST-polling одновременно по трафику, задержке и нагрузке на сервер и обеспечивает требуемое время обнаружения пропажи; REST может сравняться с ним лишь по времени обнаружения, увеличив трафик в 5,6 раза и нагрузку в 7,4 раза (N = 1 000). Это экспериментально обосновывает выбор MQTT с учётом ограничений подраздела 4.7.
